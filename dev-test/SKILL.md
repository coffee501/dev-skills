# Dev TEST

将跨业务领域的后端服务与系统集成需求和设计转化为可执行、可追踪、可维护的测试场景、测试用例、测试数据和自动化输入。采用风险驱动覆盖，不预设行业模型、技术栈、测试框架或固定测试金字塔。

## 接入 Dev 生命周期

复用输入中的正式 `CHG`；没有权威编号时使用临时 `CHG-PENDING-001`。测试产物记录来源版本、适用实现、契约、数据和环境，不把旧证据自动用于新的变更范围。

需要统一追踪时读取 [产物协议](../dev-lc/references/artifact-contract.md)；将执行任务交给验证流程或将语义缺口返回上游时读取 [交接协议](../dev-lc/references/handoff-contract.md)；需求、设计、实现、环境或预期变化时读取 [失效传播规则](../dev-lc/references/invalidation-rules.md)。测试设计基线、执行就绪、验证通过和发布门禁遵循 [状态与阶段门](../dev-lc/references/lifecycle-state-model.md)，保持相互独立。

## 保持职责边界

负责测试什么、为什么测试、如何准备、如何执行以及观察什么结果。默认不要：

- 修改业务目标、规则、状态、数据口径或验收标准
- 改变系统边界、模块职责、数据权威或架构决策
- 发明接口字段、错误码、事务、幂等、迁移或失败语义
- 用测试工具限制替代产品和设计决策
- 根据行业惯例虚构测试预期
- 仅为提高用例数量生成低价值组合
- 执行测试、修改测试代码、创建数据、安装依赖或改变环境；自动化实现交接 `dev-impl`，执行和证据治理交接 `dev-val`
- 默认覆盖客户端、前端组件、视觉或 UI/UX 测试

业务预期缺口交接 `dev-req`；架构和跨模块语义缺口交接 `dev-hld`；字段、接口、事务、错误码和实现机制缺口交接 `dev-lld`；自动化代码交接 `dev-impl`；测试执行和证据聚合交接 `dev-val`。除非用户明确要求串联执行，否则只在当前输出中形成交接项，不自动调用其他 Skill。

交接项至少包含：目标流程、问题与证据、受影响编号、来源侧严重度、目标侧影响、建议责任角色、缺失决策、受阻测试、可继续内容。来源侧严重度不自动等同于目标流程的优先级。合规、SLO、安全授权、运维或外部供应方问题交接相应责任流程，不强行归入 `dev-*` 阶段。目标 Skill 或正式责任流程不存在时输出结构化交接包。

## 建立可信输入

按以下优先级读取：

1. 已确认的 `REQ/RULE/AC`
2. `DEC/MOD/FLOW/VAL` 和 `DET/DDEC/DVAL`
3. `DATA/MIG/API/EVT/JOB/CFG` 及机器可读契约
4. 范围和版本匹配的有效 `CTX` 及其引用的 `CTXF/CTXP/CTXG`
5. 当前代码、现有测试、数据库、配置、部署和运行证据
6. 历史缺陷、事故、变更记录和当前对话结论

区分已确认、实现证据、合理推断、待确认、冲突和已废止。现有测试证明当前被检查的行为，不自动证明业务预期正确或覆盖充分。OpenAPI、AsyncAPI、Proto、JSON Schema、DDL、ORM、迁移文件和配置 Schema 存在时作为结构权威来源；发现文档冲突时显式列出。

使用 `CTXP` 发现分支、状态、数据、副作用和失败路径，使用 `CTXG` 暴露测试阻塞和未知边界；不得把As-Is行为直接
当作测试预期，预期仍须来自已确认需求、设计或其他权威判定依据。

输入没有 `dev-*` 编号时不要虚构或拒绝设计，按需分配中立标识：`SRC` 表示来源，`RISK` 表示风险，`CONTRACT` 表示契约，`DEFECT` 表示缺陷或事故。追踪可以从任一有效来源开始。

## 选择工作模式

| 模式 | 使用条件 | 默认输出 |
| --- | --- | --- |
| 测试诊断 | 输入不完整、矛盾或不可测试 | 已确认输入、覆盖缺口、P0/P1风险和结构化交接 |
| 完整测试设计 | 需要测试方案、场景和用例 | 全部适用章节、追踪、数据、环境和自动化输入 |
| 增量完善 | 需求、设计或实现发生变化 | 新增、修改、废止测试及回归影响 |
| 测试评审 | 已有测试用例需要检查 | 按严重度排序的问题、证据、影响和基线结论 |
| 回归选择 | 存量变更需要确定回归范围 | 必测、影响、条件和不回归项及依据 |
| 自动化交接 | 测试设计稳定，需要实现自动化 | 自动化候选、生命周期、层级、依赖、数据、断言和稳定性要求 |
| 执行准备交接 | 设计已稳定，需要实现自动化或运行测试 | 分别向 `dev-impl` 和 `dev-val` 输出版本化 `HOF` |

严重度统一为：

- **P0**：预期结果、核心规则、状态、数据或失败语义不明确，无法安全设计或执行关键测试，阻塞受影响分支和测试基线。
- **P1**：存在显著覆盖、兼容、安全、性能、环境或可重复性风险，基线前应解决或正式接受风险。
- **P2**：不影响当前核心覆盖的清晰度、维护性、复用性或自动化优化。

P0/P1/P2 只用于问题严重度，不用于测试优先级。测试场景和用例优先级使用 `Critical / High / Medium / Low`，依据业务影响、变更风险、发生可能性和故障可检测性确定。

## 识别测试类型

先识别新功能、已有功能变更、规则调整、缺陷修复、契约变更、系统集成、数据迁移、功能下线、架构迁移或非功能专项。只有纯新建且不共享契约、数据、配置、基础设施、部署单元或运行资源时，才跳过回归和兼容分析。

根据风险选择最低但充分的层级：

- **单元**：纯函数、算法、规则和局部状态。
- **组件**：单模块及其存储、缓存或适配器。
- **契约**：API、RPC、事件、Schema和消费者兼容。
- **集成**：多模块、数据库、中间件或外部依赖协作。
- **系统**：完整后端业务流程及系统级结果。
- **端到端**：少量关键跨系统闭环。
- **发布验证**：配置、迁移、混合版本、灰度和回滚。

不要机械套用固定测试金字塔；说明层级选择依据、替代能力和未覆盖风险。

## 执行测试设计流程

1. 核对测试目标、范围、非范围、上游编号、设计状态和未决问题。
2. 识别工作模式、变更类型、风险和适用测试层级。
3. 存在实现时建立现有测试、调用、数据、契约和运行证据基线。
4. 从 AC、VAL、DVAL、状态、数据、契约和风险提取测试场景 `TSC`。
5. 使用等价类、边界值、决策表、状态转换、成对组合和故障模型控制覆盖。
6. 将高价值场景展开为测试用例 `TC`，明确前置、数据、步骤、观察点和预期。
7. 设计适用的数据、环境、依赖替身、时间控制、清理和可重复性。
8. 对存量变更选择新增、修改、废止和回归测试。
9. 标识自动化候选及推荐层级，但不默认实现或执行。
10. 检查追踪闭环、覆盖缺口、证据有效性、冲突、可执行性和测试设计基线。

持续检查主线：

> 测试输入与范围 → 被测对象与风险 → 覆盖模型 → 场景 → 用例 → 数据与环境 → 兼容回归 → 自动化交接 → 追踪与基线

## 建立测试追踪

使用稳定标识：

- `SRC-001` / `RISK-001` / `CONTRACT-001` / `DEFECT-001`：没有上游编号时使用的中立来源
- `TSC-001`：测试场景或覆盖目标
- `TC-001`：可执行测试用例
- `TDP-001`：抽象测试数据分区、等价类或边界类
- `TD-001`：具体可执行测试数据集或夹具
- `TENV-001`：测试环境拓扑与版本基线
- `TCOND-001`：依赖状态、时间、网络或故障条件
- `AUT-001`：自动化实现映射

建立：

> `SRC/REQ/RULE/AC/VAL/DVAL/RISK/CONTRACT/DEFECT → TSC → TC → TDP/TD/TENV/TCOND → AUT`

存在完整开发链时保留：

> `REQ/RULE → AC → DEC/MOD/FLOW → DET/DDEC → DATA/MIG/API/EVT/JOB/CFG → VAL/DVAL → TSC/TC`

简单任务只编号关键节点。优先复用已有编号；增量完善不得因顺序变化重新编号。记录来源版本或摘要。废止或替代编号保留，`Superseded` 必须引用后继编号，编号不得复用。不要自行重编号任何上游标识。

验证项使用 `Planned → Passed / Failed / Blocked`。测试用例生命周期使用 `Draft → Ready → NeedsReview → Ready / Deprecated / Superseded`；执行方式单独标记为 `Manual / AutomationCandidate / Automated`。某次执行结果使用 `NotRun / Passed / Failed / Blocked / Skipped`，并关联执行批次、时间、代码和契约版本、环境和证据。生命周期、执行方式和执行结果不得混用。

上游语义、契约、实现、数据、环境或自动化断言发生实质变化时，将受影响 `Ready` 用例置为 `NeedsReview`，并使相关旧执行证据失效。`dev-test` 默认只设计 `TC → VAL/DVAL` 映射，不直接静默改写上游状态。

每个 `VAL/DVAL` 明确必选 `TC`、适用版本与环境、允许的结果和证据新鲜度，并把聚合规则交给 `dev-val`。测试设计本身不读取执行结果后改变验证状态；来源或适用范围变化时标识旧证据应重新评估。

## 设计测试场景和用例

按价值优先覆盖：核心成功、规则拒绝、状态和数据不变量、边界、权限、重复与并发、外部失败、兼容迁移、性能安全与容灾。

预期结果必须可观察并注明判定依据（oracle）：确认需求、权威契约、状态模型、数据不变量、独立参考实现、人工批准结果或其他可信来源。按适用范围检查返回、状态、数据、外部副作用、事件、日志审计、指标告警和“不应发生的变化”。不得只写“成功”“正常”或“符合预期”，也不得用被测实现自身计算同一预期。

使用决策表、状态转换、等价类、边界值、成对组合和风险优先级避免组合爆炸。不要默认把每个字段值与所有流程做笛卡尔积。

## 处理已有实现与测试

建立 As-Is 测试证据：已有测试位置、层级、断言、数据、依赖、执行方式、稳定性和最近有效结果。每条执行证据记录时间、代码或提交版本、契约摘要、环境和失效条件；缺少这些内容时只能作为弱证据。GitNexus 可用于识别符号、调用和影响半径；再结合契约、运行、数据、历史缺陷与现有测试确认回归范围。工具不可用时回退到代码和测试搜索，不得阻塞。

现有测试可能过时、断言不足或固化错误行为。将“测试存在”“最近通过”“覆盖业务预期”分开判断。不得以覆盖率百分比单独证明覆盖充分。

## 管理自动化与执行边界

自动化建议至少说明候选用例、推荐层级、数据准备、依赖替身或真实依赖、关键断言、代码位置、责任单元、执行触发、
适用版本、隔离与稳定性风险。`AUT` 是自动化规格，使用
`Draft → Ready → NeedsReview → Ready / Superseded / Deprecated`；执行方式单独记录为
`AutomationCandidate / Automated`。自动化代码由 `dev-impl` 以 `IMP(kind=test-automation)` 管理，门禁状态由
`dev-val` 或项目质量责任方记录为 `NotEnabled / Enabled / Quarantined / Disabled / Deprecated`。
创建 `AUT` 映射不等于代码已实现、执行已通过或已经进入门禁。

自动重试不得掩盖首次失败；不稳定测试不得静默移出门禁。`Quarantined` 必须记录原因、责任人、影响、恢复条件和目标时间。优先在最低可靠层级验证，跨系统端到端只覆盖无法由低层测试证明的关键闭环。同一风险可以由不同层级提供互补证据，不将跨层验证机械判为重复。

用户要求实现自动化时形成面向 `dev-impl` 的 `HOF`；用户要求运行测试时形成面向 `dev-val` 的 `HOF`。交接必须包含版本、环境、数据、副作用、费用、影响范围、隔离、清理、恢复、停止条件和授权缺口。目标模块未启用时保持阻塞，不由本 Skill 越权执行。

## 区分治理结论

分别判断，不得相互暗示：

- **测试设计基线**：场景、用例、数据、环境和预期已设计完成。
- **测试执行就绪**：所需环境、权限、依赖、数据、隔离、清理和安全授权已经具备。
- **验证通过**：指定版本和环境中的有效执行证据满足 `VAL/DVAL` 聚合规则。
- **发布门禁通过**：规定的验证已通过，剩余风险由有权限责任方接受。

## 检查测试设计基线

只有当前范围内所有适用条件满足，才标记为“测试设计基线”；不适用项说明理由：

- 测试范围、非范围、层级选择和风险优先级明确。
- 关键有效来源（包括适用的 `SRC/REQ/RULE/AC/VAL/DVAL/RISK/CONTRACT/DEFECT`）可以追踪到 `TSC/TC`。
- 适用的正常、规则拒绝、异常、边界、状态、数据和权限场景已覆盖。
- 适用的接口、事件、任务、并发、幂等和一致性风险已覆盖。
- 对存量变更，兼容、迁移、混合版本、发布、回滚和回归范围已覆盖。
- 适用的安全、性能、可靠性和容灾目标具有可执行验证设计。
- 测试数据、环境、依赖、时间控制和清理方式可以准备。
- 每个核心用例具有明确且可观察的预期结果。
- 不存在未解决的测试设计 P0，测试人员无需自行决定关键业务或架构语义。
- 所有P1已经解决，或由有权限责任方记录接受依据、责任人、跟踪项和失效条件。
- 自动化交接或人工执行方式明确，重大风险具有验证项。

基线记录文档版本、有效输入版本或摘要、评审角色、评审时间、未决风险、风险接受和重新评审触发条件。测试设计基线不表示执行就绪、验证通过或发布门禁通过。

不满足时保持“测试设计草案”，列出阻塞项、影响、责任流程和可继续内容。

## 组织输出

各模式至少保持以下固定结构：

- **诊断**：结论、有效输入、P0/P1、可继续设计、结构化交接。
- **完整设计**：使用 [references/outline.md](references/outline.md) 的适用章节且不生成空章节；至少包含范围与依据、风险与覆盖、`TSC/TC`、数据与环境、兼容回归、自动化映射、追踪与四类治理结论。
- **增量完善**：保留编号、变更差异、受影响对象、新增/修改/废止用例、失效证据、更新后的追踪与回归集。
- **评审**：总体结论、P0/P1/P2、证据与影响、基线缺口、重新评审条件。
- **回归选择**：变更依据、影响链、必测/影响/条件/不回归项、触发条件、剩余风险。
- **自动化交接**：`AUT` 规格状态、关联 `TC`、建议代码位置、责任、触发、适用版本、数据依赖、断言、隔离和稳定性治理。
- **执行准备交接**：目标模块、适用版本、环境、数据、授权、安全阻塞、预期
  `IMP(kind=test-automation)/BUILD` 或 `RUN/EVD` 产物。

完整设计、测试评审或基线判断前读取 [references/review-checklist.md](references/review-checklist.md)。局部问题只执行相关检查。
