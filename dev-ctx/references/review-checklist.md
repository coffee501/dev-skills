# 上下文评审清单

## 范围与版本

- 目标问题、消费者、仓库、模块、版本、环境和非范围是否明确？
- 多仓库、生成源、子模块和脏工作区是否分别记录？
- GitNexus或其他索引是否绑定正确仓库并具有足够新鲜度？

## 事实与证据

- 实现事实、运行事实、业务声明和推断是否分离？
- 关键 `CTXF/CTXP` 是否回指文件、符号、契约、配置或运行证据？
- 是否避免把测试存在、代码存在或配置存在解释为生产已启用和业务正确？
- 冲突证据是否并列保留而非静默选择？

## 覆盖与边界

- 入口、结果、状态、数据、副作用、失败和恢复是否满足当前消费者需要？
- 动态调用、消息、任务、共享数据库、配置路由、生成代码和仓外依赖是否检查或列为未知？
- “未发现”和“不存在”是否严格区分？
- 是否避免为了文档完整性展开与任务无关的代码？

## 可复用性

- `CTX` 是否记录适用范围、版本、新鲜度和失效条件？
- `CTXF/CTXP/CTXG` 是否具有独立版本、父 `CTX`、适用范围、证据和后继关系？
- 下游视图是否只包含可依赖事实、必要路径、未知和禁止推断内容？
- 状态为 `Ready` 时，消费者所需子制品是否均为 `Ready + Current`，且不存在命中该分支的开放阻塞 `CTXG`？
- 是否记录已知消费者或统一反向索引，能够定向发送失效 `HOF`？

## 安全与交接

- 运行证据是否处于用户授权范围，并绑定环境、版本和时间窗口？
- 是否避免复制密钥、令牌、个人数据和生产敏感值？
- 阻塞缺口、仓外证据请求、责任转移和失效通知是否使用标准 `Prepared HOF`？

按严重度输出：P0表示关键上下文错误或缺失会使下游无法安全继续；P1表示显著范围、新鲜度、冲突或动态边界风险；
P2表示不影响当前消费者的清晰度和维护性问题。不使用综合分数。
