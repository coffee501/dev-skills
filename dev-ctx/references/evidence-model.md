# 上下文证据模型

## 分离四类结论

| 类型 | 含义 | 不得自动推导 |
| --- | --- | --- |
| 实现事实 | 当前版本的代码、契约、配置或迁移明确表达的行为 | 生产已启用、业务上正确 |
| 运行事实 | 日志、指标、追踪、部署或执行结果证明的特定环境行为 | 其他版本和环境同样成立 |
| 业务声明 | 需求、手册、注释或人员说明表达的意图 | 当前实现已经遵守 |
| 推断 | 根据命名、结构、调用邻近或多项证据形成的解释 | 已确认事实 |

发现实现与业务声明不一致时分别保留，不选择一方覆盖另一方，并创建 `CTXG`。

## 证据优先级

优先使用最接近目标结论的权威来源，而不是固定相信某一种工具：

1. 目标版本的机器契约、代码、配置、迁移和生成源。
2. 与目标版本绑定的测试、构建、部署清单和运行证据。
3. 版本明确的设计、需求、运行手册和变更记录。
4. GitNexus等派生索引、静态图和自动生成说明。
5. 命名、目录、框架惯例和未验证推断。

派生索引用于发现，不替代原始证据。文档与代码冲突时记录两者的版本、适用范围和冲突类型。

## CTXF 事实判定

`CTXF` 完整字段遵循 [context-artifacts.md](context-artifacts.md)。`Observed`表示直接来源可见；`Corroborated`表示至少
两条不共享同一生成链或单一根来源的证据一致；`Inferred`表示证据支持但尚无直接来源。三者都不意味着业务正确。

源代码与由它生成的静态索引、同一配置及其生成清单、共享同一夹具的两个测试通常不算独立证据；源代码与绑定同一
版本的运行追踪、实现契约与独立契约测试可以视为独立。无法判断独立性时不得标记 `Corroborated`。

## 处理未知和负面结论

- 未找到实现时写“在已检查范围未发现”，列出范围和搜索方式，不写“不存在”。
- 动态配置、反射、依赖注入、插件、表达式、脚本、数据库触发器和仓外消费者默认不能由静态调用图完全排除。
- 无法确认或来源互相矛盾时创建 `CTXG`，不要创建 `Unknown/Conflicted CTXF`，也不要用低置信推断填空。
- 密钥、令牌、个人数据和生产敏感信息只记录存在性、位置类别和保护要求，不复制具体值。

## 证据定位与访问边界

- 证据定位器至少记录来源类型、仓库或系统、目标版本、文件或契约节点、符号或配置键；运行证据还要记录环境和时间窗口。
- 行号、截图位置和派生索引节点只作为便利定位，不作为跨版本稳定标识。
- 只读取用户已经授权且属于任务范围的运行资料。未经明确授权，不连接生产数据库、共享环境或外部日志系统。
- 默认记录结构、状态、摘要和统计信息，不复制密钥、令牌、个人数据或敏感业务值。
- 无权访问、无法脱敏或缺少版本绑定的运行证据进入 `CTXG`，不得由静态代码推断替代。
