# 下游消费视图

不要把完整上下文包无差别传给所有流程。保留稳定编号，按消费者裁剪视图。

下文中的“可消费上下文”统一指 [context-package.md](context-package.md) 定义的 `Eligible CTX`。消费者必须检查目标范围、
版本、配置、环境、最小充分性和阻塞 `CTXG`，不得自行把 `Draft/PotentiallyStale/Stale CTX` 解释为有效。

| 消费者 | 优先提供 | 明确不替代 |
| --- | --- | --- |
| `dev-req` | 当前角色入口、现有行为、编码规则、状态结果、历史兼容和语义冲突 | 业务目标、正确规则和验收确认 |
| `dev-hld` | 系统与团队边界证据、运行单元、依赖、数据权威候选、关键实现路径 | 目标架构和设计决策 |
| `dev-lld` | 具体契约、模型、表、事件、任务、配置、错误、事务和并发实现 | 新字段、错误码和实现机制决策 |
| `dev-impl` | 文件与符号、调用和数据路径、影响表面、保持项证据、现有测试 | 修改方案和完成证据 |
| `dev-test` | 可观察行为、分支、状态、数据、副作用、失败路径和现有测试 | 测试预期正确性和覆盖决策 |
| `dev-val` | 执行入口、环境条件、依赖、数据准备线索和观察点 | 正式执行结果和门禁结论 |
| `dev-rel` | 运行单元、配置、迁移、功能开关、依赖顺序和探针 | 发布计划、授权和生产执行 |
| `dev-ops` | 日志、指标、追踪、告警、运行入口、故障和恢复实现 | 运行授权、事故处置和RCA结论 |

## 最小充分性

消费者先声明当前问题和受影响分支，再判断上下文是否充分：

- `dev-req` 至少需要当前角色入口、可观察结果、现有规则证据和业务语义冲突。
- `dev-hld` 至少需要目标范围的系统边界、运行单元、关键依赖、数据权威证据或候选，以及核心实现路径。
- `dev-lld/dev-impl` 至少需要目标契约或入口、具体符号与数据路径、保持项证据、直接依赖和重要潜在影响。
- `dev-test/dev-val` 至少需要可观察行为、关键分支、状态与副作用、失败路径、环境条件和可用观察点。
- `dev-rel/dev-ops` 至少需要运行单元、环境与配置边界、迁移或开关、外部依赖、观察和恢复入口。

缺少某项只阻塞依赖它的分支。无法判断是否关键时创建 `CTXG` 并交给消费者或责任方确认，不通过扩大无关扫描来
掩盖缺口。

## 交接要求

普通引用只需传递 `CTX/CTXF/CTXP/CTXG` 编号及版本。上下文缺口阻塞下游、需要仓外信息、责任发生转移或旧上下文
失效需要通知消费者时，必须创建
`Prepared HOF`，至少说明消费者、问题、已检查范围、可靠事实、禁止推断内容、未知与冲突、补充证据责任方和恢复
条件。`dev-ctx` 不接受业务、设计、实现、测试或发布结论。
