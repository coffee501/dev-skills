# Dev LLD

将任意业务领域的后端服务与系统集成需求转化为可以编码、迁移、发布、回滚和验证的实现级设计，并与现有代码、数据和运行约束保持一致。不预设行业模型、业务对象、后端架构风格、编程语言、框架、数据库或中间件。客户端、前端组件和 UI/UX 详细设计不属于本 Skill 的默认范围。

## 接入 Dev 生命周期

复用当前变更的 `CHG`，没有权威编号时只使用临时 `CHG-PENDING-001`。详细设计产物通过版本化信封关联 `REQ/AC/DEC/MOD/FLOW`，并保持 `DET/DDEC/DATA/MIG/API/EVT/JOB/CFG/DVAL` 编号稳定。

需要产物和追踪规则时读取 [产物协议](../dev-lc/references/artifact-contract.md)；向实现和测试设计交接时读取 [交接协议](../dev-lc/references/handoff-contract.md)；设计、契约或实现事实变化时读取 [失效传播规则](../dev-lc/references/invalidation-rules.md)。`VAL/DVAL` 的非 `Planned` 状态必须由适用版本和环境中的有效执行证据支持，详细设计不得自行宣布验证通过。

共享协议不可用时仍可独立完成详细设计诊断、设计、评审和实现任务拆分，使用本地临时标识并保留来源、适用范围、
风险和证据；不得宣称正式G3、全局编号或标准HOF已经确认。

## 保持职责边界

详细设计回答“模块内部具体如何实现”。继承而不重复维护需求事实与概要设计结论。

默认不要：

- 改变业务目标、角色、资格、规则、状态语义、数据口径或验收结果
- 重新划分系统边界、模块职责、数据所有权或跨系统一致性模式
- 在没有依据时编造类名、表名、字段、接口、错误码、容量或技术组件
- 把候选方案写成已接受结论
- 用重试、补偿或临时状态替代尚未确认的外部失败、拒绝、部分成功和超时后的业务结果
- 展开完整测试步骤、测试数据和自动化脚本
- 为简单逻辑强制生成类图、状态机或伪代码
- 未经用户明确要求就修改业务代码、数据库、基础设施、配置或部署状态

业务问题交接给 `dev-req`；系统边界、模块职责、数据归属或架构决策问题交接给 `dev-hld`；完整测试用例交接给 `dev-test` 或等价测试设计流程。除非用户明确要求串联执行多个 Skill，否则不要自动调用下游，而是在当前输出中形成交接项。

每个交接项至少包含：目标流程、问题与证据、受影响编号、严重度、需要确认的决策、当前设计能否继续。P0 阻塞受影响设计分支；未受阻内容可以继续，但文档保持“详细设计草案”。目标 Skill 不存在时输出结构化交接包，不因此虚构能力或阻塞其他设计内容。

## 建立可信输入

优先读取：

1. 已确认的 `REQ`、`RULE` 和 `AC`
2. 已接受的 `DEC`、`MOD`、`FLOW` 和概要设计约束
3. 符合共享资格规则的 `Eligible CTX` 及其引用的 `CTXF/CTXP/CTXG`
4. 当前有效代码、数据库、接口、配置、部署和运行证据
5. 历史设计与变更记录
6. 当前对话中的明确结论

区分已确认、实现证据、合理推断、待确认、存在冲突和已废止。现有代码只能证明当前可能如何实现，不能单独证明业务行为正确或未来必须保留。设计名称尚未确定时使用逻辑名称，不要伪造真实类、表或接口名称。

`Eligible CTX` 已覆盖当前设计问题时直接引用其编号和版本；只对 `CTXG`、潜在过期项或详细设计所需新增深度做定向核验，
不由本 Skill 改写 `CTX` 状态。

## 选择工作模式

| 模式 | 使用条件 | 默认输出 |
| --- | --- | --- |
| 设计诊断 | 需求、概要设计或实现证据不足 | 已确认输入、缺口、阻塞影响、风险和三至五个优先问题 |
| 完整设计 | 输入基本稳定，用户需要完整详细设计 | 全部适用章节、实现单元、变更清单、验证与任务拆分 |
| 增量完善 | 新增确认、约束或实现证据 | 新增、修改、废止内容及受影响追踪节点 |
| 设计评审 | 检查已有详细设计 | 按严重度排序的问题、证据、影响和修改建议，不重写全文 |
| 实现拆分 | 设计已稳定，需要交给编码 | 按依赖顺序输出代码、数据、接口、配置、迁移和验证任务 |

统一使用严重度：

- **P0**：会导致业务或架构语义不确定、实现不可安全编码、迁移或回滚不可行，阻塞受影响分支和设计基线。
- **P1**：不会立即阻塞编码，但存在显著正确性、兼容性、安全性、性能或运维风险，基线前应解决或正式接受风险。
- **P2**：不影响当前正确性和可交付性的清晰度、维护性或演进优化。

## 识别设计类型

在展开设计前识别主类型和次类型：

| 类型 | 重点 |
| --- | --- |
| 新模块或新功能 | 实现边界、流程、状态、数据、接口和验证 |
| 已有功能变更 | 当前实现、影响半径、保持项、兼容和回归 |
| 业务规则调整 | 规则落点、生效边界、历史数据和在途处理 |
| 系统集成 | 契约、权威方、超时重试、失败语义和版本兼容 |
| 数据迁移 | 模式演进、回填、校验、切换、回退和清理 |
| 功能下线 | 调用方、数据保留、替代能力、停用顺序和退出条件 |
| 架构迁移 | 新旧实现共存、流量迁移、混合版本、回滚和临时逻辑退出 |
| 缺陷修复 | 根因、最小修改点、行为保持、回归面和修复验证 |

除纯新建且无共享契约的场景外，自动进入存量兼容分析；具体检查按参考文件路由加载。

## 选择设计深度

- **轻量**：单模块局部逻辑，聚焦实现单元、数据或接口变化、异常和验证。
- **标准**：多模块或有外部依赖，展开核心流程、数据、接口、一致性、配置和发布。
- **关键生产设计**：存在不可逆副作用、关键数据一致性、复杂迁移、高并发、高可用或严格合规要求，展开所有有依据的可靠性、回滚和运行机制。

选择最低但足够的深度。不要把完整目录当作必须填满的表单。

## 按需读取参考文件

- 创建完整文档、选择章节或图时，读取 [references/outline.md](references/outline.md)。
- 设计模块、功能或核心程序处理时，读取 [references/implementation-unit.md](references/implementation-unit.md)。
- 存在已有代码、功能变更、集成、迁移、下线或混合版本时，读取 [references/change-compatibility.md](references/change-compatibility.md)。
- 评审或执行最终基线检查时，读取 [references/review-checklist.md](references/review-checklist.md)。
- 只回答局部问题时，不读取无关文件。

## 处理已有实现

先建立实现证据基线：入口、核心符号、调用链、数据访问、接口和事件、任务、配置、部署单元、测试与已知运行行为。再按以下主线设计：

> As-Is 实现 → To-Be 实现 → Gap → Impact → 保持项 → 兼容与迁移 → 发布与回滚 → Verification

如果 GitNexus 已可用且索引有效，优先用它定位功能聚类、执行流程、符号关系和影响半径；再用源代码、测试、数据库、配置和运行资料确认。工具不可用或索引陈旧时回退到代码搜索和入口追踪，不得阻塞设计。不得把聚类名称直接当作业务模块，也不得把“未发现”写成“不存在”。

## 执行详细设计流程

1. 核对 `REQ/RULE/AC`、`DEC/MOD/FLOW/VAL`、范围、约束和未决问题。
2. 识别设计类型、工作模式和设计深度，读取适用参考文件。
3. 存在已有实现时建立代码级 As-Is 基线和影响清单。
4. 将概要模块拆为可实现、可验证的详细设计单元 `DET`。
5. 设计正常、分支和异常流程；在适用且业务结果已经确认时设计重试、补偿以及状态和数据变化。
6. 定义适用的表字段与约束、接口与事件契约、算法和配置。
7. 落实事务、并发、幂等、一致性、安全、性能、异常和可观测性机制。
8. 对变更设计兼容、迁移、混合版本、发布顺序、回滚和退出条件。
9. 建立 AC、设计单元、实现对象与 `VAL` 的追踪，拆分实施任务。
10. 检查上下游边界、图文一致性、可编码性、可回滚性和详细设计基线。

持续检查主线：

> 设计输入 → 实现结构 → 功能实现 → 流程与状态 → 数据与接口 → 一致性与可靠性 → 兼容迁移与发布 → AC 验证

## 建立实现追踪

为核心实现分配稳定标识：

- `DET-001`：详细设计单元
- `DATA-001`：数据结构
- `MIG-001`：数据、契约或运行状态迁移单元
- `API-001` / `EVT-001` / `JOB-001`：同步接口、事件或任务
- `CFG-001`：关键配置
- `DDEC-001`：只影响模块内部实现的重要详细设计决策
- `VAL-001`：继承自需求或概要设计的验证项
- `DVAL-001`：详细设计新增的实现级验证项

建立：

> `REQ/RULE → AC → DEC/MOD/FLOW → DET/DDEC → 代码/DATA/MIG/API/EVT/JOB/CFG → VAL/DVAL`

对存量变更增加：

> `REQ-CHG → DEC/MOD/FLOW → DET/DDEC → 受影响符号与契约 → 兼容策略 → MIG/发布/回滚 → VAL/DVAL 回归`

简单设计只编号关键节点。优先复用现有编号；增量完善时不得因章节顺序变化而重新编号。已删除或替代的编号保留并标记 `Deprecated` 或 `Superseded`，不得重新分配；发现冲突时创建新编号并记录替代关系。修改任一节点时检查全部下游影响，不只检查相邻章节。不要自行重编号上游 `REQ/RULE/AC/DEC/MOD/FLOW/VAL`。

验证项使用 `Planned → Passed / Failed / Blocked`，不要套用决策状态。详细设计只创建或维护 `Planned` 目标；`Passed/Failed/Blocked` 必须引用 `dev-val` 产生的适用 `EVD`。继承的 `VAL` 保持原目标和编号；详细设计新增验证使用 `DVAL`。验证范围实质变化时创建新的 `DVAL` 或明确版本关系，不静默改写既有验证含义。

## 管理详细设计决策

只有模块内部存在重要取舍时才创建 `DDEC`，记录设计问题、关联输入、候选方案、选择、依据、代价、风险和验证方式。沿用 `Proposed → Accepted → Validated`，以及 `Superseded` / `Deprecated` 状态。

由本 Skill 新生成、推导或推荐的 `DDEC` 一律从 `Proposed` 开始，代理不得自行接受，即使它看起来是唯一安全方案。只有输入材料或当前对话按照项目决策权限明确选择了该项具体实现机制，才能标记为 `Accepted`，并记录确认依据。需求目标、约束、技术必要性、用户要求“生成文档”或对业务结果的确认，都不能代替对具体实现方案的接受。

依赖外部系统能力的选择还要记录能力证据或验证项。决定安全性、可实现性、数据可恢复性或回滚能力的关键决策，关联 `VAL/DVAL` 通过前不得标记为 `Validated`。

如果选择会改变业务含义，交接 `dev-req`；如果会改变系统边界、模块职责、数据权威或概要一致性策略，交接 `dev-hld`。不要用 `DDEC` 绕过上游决策。

## 控制实现级设计

- **模块设计**：写清职责、输入输出、前置条件、处理步骤、规则、状态、数据、接口、异常、权限、日志、兼容和验证。
- **数据设计**：只有发生持久化或数据变化时展开字段、约束、索引、访问模式、生命周期和迁移。
- **接口设计**：同时覆盖 REST、RPC、事件、消息、回调、定时任务和批处理，不把所有交互都叫 API。
- **事务与并发**：具体到事务起止、竞争资源、锁或版本位置、冲突结果、幂等键和补偿入口；没有竞争或跨边界结果时不要过度设计。
- **安全**：具体到认证信息来源、校验位置、数据过滤、敏感字段和审计事件。
- **性能与可用性**：只根据已确认指标展开耗时预算、容量、缓存、限流、降级和恢复；没有指标时记录缺口。
- **日志与监控**：具体到关键事件、字段、Trace、指标、告警条件和处置入口，但避免记录敏感数据。
- **配置与发布**：定义默认值、作用域、变更方式、发布顺序、兼容窗口、回滚和临时设计退出条件。

以上技术形态均为条件检查维度，不是默认技术选型。只展开输入材料或现有实现实际涉及的部分；使用项目自己的业务术语、工程结构和技术栈，不将模板示例强加给项目。

项目已经使用 OpenAPI、AsyncAPI、Proto、JSON Schema、DDL、ORM 模型、迁移文件或配置 Schema 等机器可读契约时，将其作为对应结构的权威来源；详细设计引用并解释关键语义，不重复维护另一份易漂移的完整定义。发现文档与权威契约不一致时列为冲突。

## 选择图和表达方式

- 跨模块或跨系统调用使用时序图。
- 复杂生命周期使用状态机或状态转换表。
- 多分支程序控制使用程序流程图或伪代码。
- 复杂对象关系使用类图；普通分层不强制画类图。
- 数据关系变化使用物理 ER 图；字段细节保留在表结构中。
- 复杂规则优先使用决策表、公式或输入输出样例。

同一信息只保留一个权威定义。模块章节引用 `DATA/API/EVT/CFG` 编号，不重复复制完整字段或契约。

## 检查详细设计基线

只有当前范围内全部适用条件同时满足，才标记为“详细设计基线”；不适用项必须说明理由：

- 需求、验收条件和概要设计输入可以追踪，不存在未解决的上游或详细设计 P0。
- 每个核心功能具有明确实现单元、职责、输入输出、处理步骤和失败结果。
- 适用的外部拒绝、超时、部分成功和不可逆副作用后的业务状态与调用方结果已经由需求确认。
- 适用的关键状态和数据变化具有合法转换、完整性约束和明确落点。
- 适用的接口、事件和任务具有字段级契约、失败语义、兼容和治理机制。
- 事务边界、竞争资源、幂等和补偿在适用场景中已经落实。
- 适用的权限、安全、日志、监控、配置和性能设计已经完整，并具有实现位置和责任单元。
- 对存量变更，已识别受影响代码、调用方、数据、任务和部署单元。
- 对数据、契约或运行方式变更，已明确迁移、混合版本、发布、回滚和退出条件。
- 每项重大风险和每条关键 AC 至少关联一个 `VAL` 或 `DVAL`。
- 普通关键 `DDEC` 至少达到 `Accepted`；决定安全性、可实现性、数据可恢复性或回滚能力的关键 `DDEC` 达到 `Validated`。外部能力假设具有证据或阻塞验证项。
- 变更清单和实现任务具有依赖顺序，研发不需要自行补充关键业务或架构决策。

不满足条件时保持“详细设计草案”，列出阻塞项、影响和责任层级。

## 组织输出

- **诊断**：输入完整度、实现理解、阻塞项、风险、建议动作和优先问题。
- **完整设计**：使用 [references/outline.md](references/outline.md) 的适用章节，不生成空章节。
- **增量完善**：说明新增、修改、废止内容，更新变更清单与追踪链。
- **评审**：按 P0/P1/P2 列出问题、证据、影响、修改建议和基线结论。
- **实现拆分**：按依赖顺序列出代码、数据、接口、配置、迁移、验证和回滚任务。

## 形成下游输入

向 `dev-impl` 提供实现单元、程序流程、数据和接口契约、异常与一致性机制、配置、迁移、发布顺序和详细变更清单；目标模块尚未启用时输出标准 `HOF`，不得把“已交接”写成“已实现”。

向 `dev-test` 或等价测试设计流程提供 `REQ/RULE/AC/VAL/DVAL` 映射、状态转换、字段和接口边界、错误码、异常、并发、幂等、兼容、迁移、性能和安全验证点；不要替代其生成完整测试用例。目标 Skill 不存在时直接输出该测试设计输入包。

生成完整设计、执行设计评审或判断设计基线前，读取 [references/review-checklist.md](references/review-checklist.md)，删除重复概要说明、无依据机制、空章节和无法追踪的实现结论。局部问题只执行与当前范围直接相关的检查。
