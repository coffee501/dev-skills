# Dev LLD

将后端服务与系统集成需求转化为可以编码、验证、兼容和迁移的实现级设计。覆盖模块内部实现、数据与契约、事务并发、安全可靠性、配置、迁移和实现交接；客户端、前端组件、UI/UX、生产发布操作、灰度排期和运维值守不属于默认范围。

## 边界与硬约束

详细设计回答“模块内部具体如何实现”。继承 `dev-req` 的业务目标、规则、验收口径，以及 `dev-hld` 的系统边界、模块职责、数据归属和架构决策；不得用实现选择改写上游结论。

默认不要：

- 改变业务目标、规则、状态语义、数据口径、验收结果、系统边界、模块职责或数据权威。
- 在没有依据时编造类名、表名、字段、接口、错误码、容量、组件或外部能力。
- 把候选方案写成已接受结论，或用 `DDEC` 绕过上游决策。
- 用重试、补偿、临时状态或技术兜底替代未确认的外部拒绝、超时、部分成功和不可逆副作用后的业务结果。
- 展开完整测试用例、测试数据、自动化脚本或生产发布步骤。
- 未经用户明确要求修改业务代码、数据库、基础设施、配置或运行状态。

业务问题交给 `dev-req`；架构、模块边界和数据归属问题交给 `dev-hld`；完整测试用例交接给 `dev-test` 或等价测试设计流程。除非用户明确要求串联执行多个 Skill，否则只输出交接项。

## 生命周期协议

复用当前 `CHG`；无权威编号时只用 `CHG-PENDING-001`。详细设计通过版本化信封关联 `REQ/AC/RULE/DEC/MOD/FLOW/VAL`，并保持 `DET/DDEC/DATA/MIG/API/EVT/JOB/CFG/DVAL` 编号稳定。

需要产物规则时读取 [产物协议](../dev-orch/references/artifact-contract.md)；交接时读取 [交接协议](../dev-orch/references/handoff-contract.md)；事实变化时读取 [失效传播规则](../dev-orch/references/invalidation-rules.md)。共享协议不可用时可独立输出草案和本地编号，但不得宣称正式 G3、全局编号或标准 HOF 已确认。

## 输入证据

优先读取并标注版本和证据状态：已确认 `REQ/RULE/AC`；已接受 `DEC/MOD/FLOW`；适用 `Eligible CTX` 及 `CTXF/CTXP/CTXG`；当前代码、数据库、接口、配置、部署和运行证据；历史设计、变更记录、当前对话明确结论。

区分已确认、实现证据、推断、待确认、冲突和已废止。现有代码只能证明当前可能如何实现，不能单独证明业务正确或未来必须保留。名称未确认时用逻辑名称，不伪造真实类、表或接口名。`Eligible CTX` 已覆盖时直接引用编号和版本；只对潜在过期项或新增深度做定向核验。

## 工作模式

支持五种模式：设计诊断输出输入完整度、缺口、阻塞影响、风险和优先问题；完整设计输出适用章节、`DET`、变更清单、验证与任务拆分；增量完善说明新增、修改和废止；设计评审输出 P0/P1/P2 问题和基线结论；实现拆分输出按依赖排序的代码、数据、接口、配置、迁移、验证和恢复任务。

`P0` 阻塞安全编码、迁移、回滚或基线；`P1` 是显著正确性、兼容性、安全性、性能或运行风险；`P2` 是不影响当前正确性和交付的优化项。

## 入口判断

先识别类型、模式和最低足够深度。常见类型：新模块、已有功能变更、规则调整、系统集成、数据迁移、功能下线、架构迁移、缺陷修复。除纯新建且无共享契约外，自动进入存量兼容分析。

深度选择：轻量聚焦 `DET`、数据或接口变化、异常和验证；标准覆盖多模块、外部依赖、一致性、配置和兼容；高风险覆盖不可逆副作用、关键数据一致性、复杂迁移、高并发、高可用或严格合规。不要把完整目录当作必须填满的表单。

## 最短流程

1. 核对 `REQ/RULE/AC`、`DEC/MOD/FLOW/VAL`、范围、约束、证据和未决问题。
2. 识别类型、模式、深度，并读取适用参考。
3. 有已有实现时建立 As-Is 基线：入口、核心符号、调用链、数据、接口、事件、任务、配置、部署单元、测试和运行行为。
4. 将概要模块拆成可实现、可验证的 `DET`，并定义必要的 `DATA/MIG/API/EVT/JOB/CFG/DDEC`。
5. 说明正常、分支、异常、状态、数据、副作用、事务、并发、幂等、安全、可观测性和可靠性；复杂单元按参考补伪代码或等价表达。
6. 对存量或共享契约变更补兼容、迁移、混合版本、技术实施依赖、回退可行性和退出条件。
7. 建立 `AC` 到实现落点、可观察结果、共享契约及 `VAL/DVAL` 的映射，拆分实现任务。
8. 用评审清单检查可编码性、可回滚性、追踪闭环、图文一致性和详细设计基线。

主线：`设计输入 → 实现单元 → 流程与状态 → 数据与契约 → 一致性与可靠性 → 兼容迁移与实施依赖 → AC 验证`。

## 追踪与状态

稳定编号：`DET-001`、`DDEC-001`、`DATA-001`、`MIG-001`、`API-001`、`EVT-001`、`JOB-001`、`CFG-001`、`VAL-001`、`DVAL-001`。

维护链路：`REQ/RULE → AC → DEC/MOD/FLOW → DET/DDEC → DATA/MIG/API/EVT/JOB/CFG/代码位置 → VAL/DVAL`。每条适用 `AC` 说明实现落点、可观察结果、引用契约、验证项和缺口。`VAL/DVAL` 不得改写或替代 `AC`。

优先复用现有编号；增量完善不得因章节顺序变化而重编号。废止或替代的编号保留并标记 `Deprecated` 或 `Superseded`。不要自行重编号上游 `REQ/RULE/AC/DEC/MOD/FLOW/VAL`。

`VAL/DVAL` 使用 `Planned → Passed / Failed / Blocked`。详细设计只创建或维护 `Planned` 目标；非 `Planned` 状态必须由适用版本和环境中的有效执行证据支持，通常引用 `dev-val` 产生的 `EVD`，不得自行宣布验证通过。

`DDEC` 只用于模块内部重要取舍。新 `DDEC` 从 `Proposed` 开始；只有授权范围内的局部技术选择或责任方明确决定具体机制后才能标记 `Accepted`。决定安全性、可实现性、数据可恢复性或回滚能力的关键 `DDEC`，在关联 `VAL/DVAL` 通过前不得标记为 `Validated`。

## 输出与交接

面向用户的完整设计使用 [references/outline.md](references/outline.md) 的适用章节，不生成空章节。内部交互只作为状态、追踪或交接包管理，不替代用户可读设计文档。

向 `dev-impl` 提供 `AC` 到实现落点及可观察结果的映射、`DET`、流程、数据和接口契约、异常与一致性、配置、迁移、技术依赖、回退边界和变更清单；目标模块尚未启用时输出标准 `HOF`，不得把“已交接”写成“已实现”。

向 `dev-test` 提供 `REQ/RULE/AC/VAL/DVAL` 映射、状态、字段、接口、错误码、异常、并发、幂等、兼容、迁移、性能和安全验证点；不要替代其生成完整测试用例。

存在前端消费方时，向 `dev-fia` 提供版本化 `API/EVT`、机器契约、业务语义来源、状态与错误、权限和数据范围、异步最终性、兼容窗口及版本过渡。详细设计不生成前端代码，也不把 OpenAPI 当作最终交付。

## 基线结论

只有当前范围内全部适用条件满足，才标记为“详细设计基线”：上游输入可追踪；无未解决 P0；关键 `AC` 已关联实现落点、可观察结果和验证项；核心 `DET`、数据、契约、事务并发、安全可靠性、兼容迁移和实现任务足以支持无歧义编码；关键风险和关键 `AC` 至少关联一个 `VAL` 或 `DVAL`；重大 `DDEC` 状态与证据匹配。

不满足条件时保持“详细设计草案”，列出阻塞项、影响、责任层级和重新进入基线评审的完成条件。
