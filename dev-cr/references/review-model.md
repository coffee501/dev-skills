# 代码评审模型

## 对象与状态

`REV`绑定一个明确的基础版本、目标版本和评审范围。状态使用：

- `Planned`：范围和输入正在准备。
- `InReview`：实际差异和影响正在评审。
- `Approved`：范围充分，未解决P0/P1为零，限制不阻止结论。
- `ChangesRequested`：存在需要整改的P0/P1或批准条件不足。
- `Blocked`：差异、预期、生成源或关键上下文不足。
- `Superseded`：基础/目标、范围或关键依据变化，旧结论被替代。

`REV`版本用于同一评审对象的补充和复审；基础或目标变更较大时创建后继编号。保留旧发现及处置，不覆盖历史。

## 评审范围

至少记录仓库、base/head或候选摘要、文件/模块、生成源、契约、迁移、配置、测试、明确不在范围的内容和无法检查的内容。工作区评审还需记录脏文件、用户已有修改和未跟踪文件。

只评审片段、单文件或局部提交时，结论必须限定到该范围，不得升级为整个候选批准。

## 发现结构

每个发现包含：

- 稳定发现ID和 `P0/P1/P2`。
- 文件、符号、契约节点或稳定定位器。
- 触发条件和可观察失败结果。
- 直接证据与推断边界。
- 影响对象、数据、调用方或运行结果。
- 违反的需求、设计、仓库规则或安全不变量。
- 责任路由、最小整改目标和验证条件。
- 状态：`Open / Addressed / AcceptedRisk / Invalid / Superseded`。

风险接受必须具有权限、范围、期限和失效条件；评审Skill不能自行接受。

## 结论规则

`Approved`要求：完整身份、充分范围、实际差异已读、关键影响已检查、P0/P1处置完成、限制不阻止判断。没有发现问题只是一项事实，不是充分条件。

`ChangesRequested`不表示所有代码都错误；未受影响且边界独立的工作仍可继续。`Blocked`说明证据不足，不等同于实现失败。

## 评审与验证分离

静态评审可以证明代码结构、明显路径、契约差异和潜在风险；运行结果由 `BUILD/RUN/EVD` 证明。评审可以要求验证，但不得把“看起来可行”登记成测试通过，也不得用测试通过消除未修复的确定性代码缺陷。
