# 调度协议

本协议供调度 Agent 或承担同等职责的主会话按需读取。它定义如何使用 Dev Skills 协调多阶段工作，不改变
`artifact-contract.md`、`lifecycle-state-model.md`、`handoff-contract.md` 和 `invalidation-rules.md` 的语义。

路线与执行投影的结构和边界以 [生命周期路线与执行投影契约](orchestration-interface.md) 为准。

所有调度中间状态遵循 `external-state-contract.md`，保存在项目外部。项目目录只接收用户明确确认的最终产物。

## 1. 何时使用调度

满足以下任一条件时，适合使用调度 Agent：

- 用户要求端到端开发交付、跨模块改造、系统集成、复杂迁移实现或架构迁移。
- 工作预计跨越三个或更多专业 Skill。
- 多个阶段需要并行推进、版本对齐、失效传播或反复交接。
- 需要从已有 `CHG/HOF/LCV` 恢复中断的工作。

以下情况由 `dev-orch` 直接调用专业 Skill：

- 请求只涉及一个明确阶段。
- 两个阶段之间依赖简单，不需要并行、失效传播或正式交接治理。
- 用户只要求解释、检查或生成一个局部产物。

调度是按需能力，不是所有变更的前置门。

## 2. 运行模式

### 路由模式

用于用户只要求路线规划，或必要的专业执行能力无法获得。先建立或复用当前 `lifecycle_route_ref`，
再输出执行投影、最小任务包、阻塞和授权缺口，不假装已经执行专业阶段。

### 协调模式

用户已要求实际推进且目标仍在授权范围内时使用。按任务权限、并行价值与独立性选择在当前上下文执行专业 Skill，或将专业任务交给独立执行上下文；调度 Agent 维护依赖、状态和结果收敛。

协调模式分为：

- `session-coordinate`：使用当前会话内可用的执行能力，不持久化控制对象；无需独立上下文的任务可顺序执行；适合一次会话内完成且无需恢复的工作。
- `durable-coordinate`：同时具有符合外置状态契约的状态服务，保存当前 `CHG/HOF/LCV` 和 `WIT`。

Codex 或 Claude Code 提供原生子 Agent 时，调度器应使用最浅的充分任务树；达到限制时等待容量，或在有权限的当前上下文顺序执行。不满足必要隔离或权限的分支才阻塞，不能把派生失败解释为专业阶段失败。平台差异读取 [调度映射](platform-mapping.md)。

发布、生产迁移、流量操作和生产运维不属于本套件调度路线。涉及真实数据或外部系统副作用的开发与验证动作仍需在对应边界取得精确授权。

## 3. 状态重建

每次启动或恢复时按以下顺序重建状态：

1. 取得当前 `lifecycle_route_ref` 和 `CHG` 引用；不存在时依据有效输入建立路线快照或注明缺口。
2. 读取路线版本、输入指纹、阶段硬依赖、进入条件、期望产物、停止条件和不适用节点。
3. 读取开放 `HOF`、阻塞和失效视图；输入变化时按失效规则重新评估。
4. 恢复ORCH拥有的 `WIT` 或会话内 `SWI`，核对任务输入指纹和路线版本。
5. 发现输入变化或状态冲突时停止受影响任务，评估 `route_change_request`，必要时产生后继路线。

存在外置状态服务时首先调用 `workspace_resolve` 获取 `workspace_id`。状态服务不可用时不在项目中创建替代状态目录；
需要可恢复状态则使用 `route-only`，无需恢复且用户要求当前会话执行时可使用 `session-coordinate`。

聊天内容可以提供线索，不能替代正式产物、仓库事实、验证证据或授权记录。

## 4. 将当前路线编译为任务图

1. 逐个读取当前路线节点，以稳定 `node_id` 解析依赖；拒绝重复、悬空或成环的依赖，不在编译时改变阶段及其硬依赖。
2. 为适用节点建立 `WIT/SWI`，绑定路线版本、输入指纹、目标专业 Skill、责任对象、预期产物和停止条件。
3. 仅当节点硬依赖满足、使用同一有效输入版本且不会并发修改同一责任对象时安排并行。
4. 标记为不适用的节点不得派发；需要补充阶段时先评估 `route_change_request`，形成后继 `LCV`。
5. 专业结果返回后检查任务包完整性和引用身份，再以产物、证据、风险与交接引用重新评估生命周期状态。
6. 收到后继 `lifecycle_route_ref` 后，只重新编译受影响任务；保留旧任务和路线引用用于审计。

当适用 `dev-impl` 节点产生可评审候选并满足对应 `dev-cr` 节点的进入条件时，调度器自动分派该评审节点；这里的“自动”
是确定性执行当前路线，不是依赖隐式 Skill 发现，也不授权在未启动 `dev-orch` 的普通单阶段请求中扩展任务。

当宿主支持命名 Agent 的续接和停止时，后续修正优先恢复原 Agent 上下文，不重复创建同一责任任务；输入已失效的运行分支应先停止，再按新版本重新派发。此规则不适用于实现候选的独立评审：`dev-cr` 不得续接产生被审查 `IMP` 的 Agent 或执行上下文，优先使用独立评审上下文。无法隔离时按 `dev-cr` 契约记录 `NotEstablished`；只有项目政策允许且 `REV` 明确记录充分的 `CompensatingControls` 证据和复核责任人时，才能考虑 `Approved`。同一上下文自查不能直接批准。

常见但非强制的并行关系：

- `dev-test` 在G1需求基线形成后立即建立 `TSC/TC Draft`，并随 HLD、LLD 和实现逐步细化，不等待G3完成才启动。
- `AUT Ready` 后可派发 `dev-impl` 实现测试代码；该分支可以与产品实现并行，但二者都必须形成当前候选的 `BUILD`
  和适用 `REV`，才可作为正式G5输入。
- 存在前端消费方时，`dev-fia` 在适用 `API/EVT` 或机器契约达到可引用版本后开始；它可以与实现和测试细化并行，
  但上游契约变化必须先触发 `FIA` 失效检查。
- 不修改同一文件或契约的多个实现任务可以并行。
- `dev-cr` 必须基于明确的产品或测试自动化实现候选版本；`dev-val` 必须区分实现自测与独立验证证据，并拒绝把只有
  `AUT` 规格、没有可执行人工路径或已实现自动化路径的用例视为G5就绪。
- `dev-fia` 的 `Ready` 只表示联调输入就绪，不表示前端实现、接口实现、测试或验收通过。

## 5. 专业任务包

每个派发任务至少包含：

| 字段 | 内容 |
| --- | --- |
| 变更 | `CHG`、目标和变更类型 |
| 任务 | `WIT`、当前 `lifecycle_route_ref/route_version/node_id`、目标专业 Skill、任务目标和责任边界 |
| 输入 | 产物编号、版本、事实来源和适用范围 |
| 范围 | 包含项、非范围、允许修改的对象 |
| 约束 | 保留行为、兼容要求、风险和授权边界 |
| 输出 | 期望产物、证据、验证方式和 `HOF` 目标 |
| 控制 | 进入条件、停止条件、阻塞上报条件 |

只传递完成任务所需的最小上下文。接收方必须按其专业 Skill 工作，不能由调度 Agent 预写专业结论。

每个 `WIT` 必须带稳定工作项编号、输入指纹、尝试次数、归属对象和当前 Agent ID。返回结果的输入指纹与当前版本不一致时不得接收。

## 6. 结果收敛

调度 Agent 对返回结果只做控制面检查：

- 产物身份、版本、来源、范围和状态是否明确。
- 预期验证是否有证据，失败是否已分类。
- 是否产生新的风险、未决项、可能失效关系、路线变化或授权缺口。
- 返回的 `HOF` 引用是否完整且状态没有越权提升。
- 下游任务的输入版本是否与当前 `lifecycle_route_ref` 一致。

内容正确性、设计接受、评审结论和验证结论由对应专业模块负责；`dev-orch` 依据证据评估阶段适用性、失效、质量门和生命周期状态，有权限责任方负责确认。

## 7. 失败、恢复与停止

- 任务失败或超时时，保留已取得证据，标记受影响分支为阻塞；不要无界重试。
- 交接被拒绝时，保留拒绝引用，停止依赖该交接的任务并评估 `route_change_request`。
- 输入疑似失效时，不删除旧产物；停止受影响任务并依据证据执行失效判断。
- 用户撤回范围、授权不足、专业结论相互冲突或任务越过开发阶段边界时停止相关分支，其他独立分支可继续。
- 所有调度任务进入终态且结果完成收集时记录 `coordination_status: Completed`；`lifecycle_status` 只引用当前LCV，
  不得由调度完成推导阶段门或 `CHG Completed`。
