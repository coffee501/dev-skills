# Dev ORCH

把 `dev-lc` 提供的生命周期路线编译为执行任务图，负责依赖内调度、并行任务、Agent状态、失败停止和结果收敛。`dev-orch` 是运行时调度器，不是生命周期规则、需求、设计、实现、评审或验证责任人。

本 Skill 设计为显式调用：Codex 使用 `$dev-orch`；Claude Code 使用 `/dev-skills:dev-orch` 或 `dev-orch` Agent。平台入口共享本文件，不复制调度语义。

## 读取控制协议

开始前读取 [生命周期—调度接口](../dev-lc/references/orchestration-interface.md)，再按任务需要读取：

- 任务图编译、任务包、收敛和恢复：[调度协议](../dev-lc/references/orchestration-protocol.md)
- `CHG/HOF/LCV/WIT` 外置持久化与项目写入边界：[外置状态契约](../dev-lc/references/external-state-contract.md)
- Codex、Claude Code 与无子代理宿主的工具映射：[平台调度映射](references/platform-mapping.md)
- 输入或产物版本发生变化：[失效传播规则](../dev-lc/references/invalidation-rules.md)
- 需要拆分阶段、任务包、Agent 或交接时：[复杂度与拆分治理](../dev-lc/references/complexity-governance.md)

接口或当前生命周期路线不可用时，不自行补造权威路线；只报告 `lifecycle_route_status: missing`、可准备的非权威输入和恢复条件，不得宣称正式 `CHG/HOF/LCV`、阶段门或持久化状态已经建立。

## 选择最小运行模式

| 模式 | 条件 | 行为 |
| --- | --- | --- |
| `direct` | LC路线只有单一专业阶段，或简单双阶段且没有协调价值 | 返回直接调用建议，不创建调度任务图 |
| `route-only` | 用户只要求规划；子代理不可用；或任务要求可恢复状态但状态服务不可用 | 基于当前LC路线输出执行投影、任务包、阻塞和授权缺口，不改写路线 |
| `session-coordinate` | 用户要求本次会话实际推进，原生子代理可用，但外置状态服务不可用 | 在当前会话内协调；明确不可恢复，不创建项目内状态 |
| `durable-coordinate` | 用户要求实际推进，原生子代理和符合契约的外置状态服务均可用 | 引用版本化 `CHG/HOF/LCV`，以ORCH拥有的 `WIT` 协调和恢复 |

不要因为用户使用 `$dev-orch` 就机械运行全部 Skill。只有当前LC路线跨三个以上专业阶段，或需要并行、反复交接或中断恢复时才进入协调模式。
复杂度治理在本 Skill 中只约束调度控制面；技术方案和实现拆分是否合理仍由对应专业 Skill 判断。

## 建立调度上下文

1. 取得 `lifecycle_route_ref`、`route_version`、适用阶段、硬依赖、进入条件、期望产物和停止条件。
2. 没有当前路线时调用或派发 `dev-lc` 建立 `LCV` 或明确的 `LCV-PENDING` 快照；无法取得时停止任务图生成。
3. 核对路线输入指纹、开放 `HOF`、失效影响和阻塞仍为当前状态。
4. 将每个适用路线节点映射为 `WIT/SWI`；跳过LC标记为不适用的阶段。
5. 只在LC硬依赖约束内选择顺序、并行组和Agent，不增加、删除或改写生命周期阶段。

聊天记录可以提供线索，但不能替代仓库事实、正式产物、验证证据、状态服务或授权记录。

## 协调专业工作

进入协调模式时，先确认系统、开发者、仓库 `AGENTS.md` 和宿主策略允许使用子代理；任何更高优先级限制都覆盖本 Skill。若不允许，切换 `route-only`，不得规避策略。随后：

1. 为每个节点创建最小任务包：目标 Skill、输入版本、范围、允许修改对象、保持项、期望产物、验证方式、停止条件和阻塞上报条件。
2. 每个子代理只拥有一个明确专业责任或互不冲突的文件范围；不得让多个子代理无边界修改同一对象。`dev-cr` 必须与产生被审查 `IMP` 的 Agent 和执行上下文隔离。
3. 仅并行没有硬依赖、使用同一有效输入版本且不会争用同一责任对象的任务。
4. 优先续接相同专业责任的已有子代理；不得让 `dev-cr` 续接被审查实现的 `dev-impl` 上下文。输入失效时先停止受影响分支，再按新版本重新派发。
5. 专业结果返回后只做调度面检查：任务身份、输入版本、范围、返回产物引用、证据位置和运行状态是否完整。
6. 内容正确性由相应专业 Skill 负责；调度器不重写专业结论，不替代实现审查或验证。
7. 出现新范围、输入失效、交接拒绝或路线缺口时停止受影响任务并形成 `route_change_request`；只有 `dev-lc` 产生后继路线后才重新编译任务图。
8. 子代理失败或超时时保留证据和原因，只处理当前路线允许恢复的分支，禁止无界重试。

适用 `dev-impl` 返回可评审候选并满足LC路线中的评审进入条件后，自动分派对应 `dev-cr` 节点；这属于执行既有路线，
不是ORCH新增阶段。若路线遗漏评审节点、评审节点未覆盖候选，或无法建立独立评审上下文，提交
`route_change_request` 或保持G4阻塞，不得直接进入正式G5。

`session-coordinate` 不创建正式 `WIT`。使用会话内 `SWI-001` 任务包，至少包含目标 Skill、输入摘要/指纹、范围、责任对象、
期望输出、停止条件和状态；编号只在当前会话内有效。进入 `durable-coordinate` 时再由状态服务创建正式 `WIT`，不得把 `SWI` 冒充已持久化对象。

Codex 中使用原生子代理完成独立专业任务；不要为子任务创建用户可见的新任务或线程。Claude Code 中使用已注册 `dev-orch` Agent 的专业 Agent 调度能力。具体工具名称和降级规则读取平台映射。

## 保持权限和状态边界

- 调度器自身不编写专业产物、不修改业务仓库、不执行测试、发布或生产命令；实际开发工作交给对应专业 Skill 上下文。
- 子代理只能执行用户已授权范围内的开发阶段工作；真实数据、外部系统和副作用仍需到达目标边界时的精确授权，发布和生产操作不进入本套件路线。
- 不把 `Prepared` 当成 `Accepted`，不把 `Suggested` 当成 `Confirmed`，不把本地检查当成正式 `EVD/GATE`。
- 不创建或改写 `CHG/HOF/LCV` 的生命周期语义；外置状态中只引用LC提供的版本并管理ORCH拥有的 `WIT`。
- 中间状态、草稿、任务运行记录和日志不得写入业务项目。
- `session-coordinate` 只能依赖当前会话内状态，必须报告 `state_persistence: none`；不得伪造可恢复性。
- 只有符合外置状态契约的服务可支撑 `durable-coordinate`。状态服务不可用时不得自行创建替代数据库或目录。

## 停止与完成

以下情况停止受影响分支：输入失效、责任冲突、缺少关键业务或设计决策、达到子代理深度/并发限制、授权不足、用户撤回范围，或继续工作会造成未授权副作用。独立且输入可靠的分支可以继续。

所有 `WIT/SWI` 均进入终态且返回结果已收集时，只能报告 `coordination_status: Completed`。`lifecycle_status` 必须引用
`dev-lc` 当前 `LCV` 或标记 `NotAssessed`；调度完成不等于阶段门通过、`CHG Completed`、风险已接受或专业结论正确。

## 输出

每轮保持简洁并提供：

- `mode` 与 `state_persistence`
- `lifecycle_route_ref`、`route_version` 和只读 `CHG` 引用
- 基于当前路线的任务图以及串行与并行关系
- 已完成、运行中、阻塞和失效分支
- `route_change_request`、开放授权和调度阻塞
- `coordination_status`、只读 `lifecycle_status`、恢复条件和停止条件

单阶段请求只给出直接路由；不要为了展示调度能力而生成空的生命周期报告。
