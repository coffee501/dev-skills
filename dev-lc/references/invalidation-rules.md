# Dev 体系失效传播规则

## 目标

上游发生实质变化时，识别需要复审的下游产物和不再有效的证据，同时保留历史和可审计关系。

## 传播流程

1. 记录变化来源、旧版本、新版本和变化摘要。
2. 沿追踪链查找直接和间接受影响对象。
3. 先标记 `PotentiallyAffected`，不得仅凭相邻关系直接宣布全部失效。
4. 根据语义、契约、实现、数据和环境差异判断实际影响。
5. 对需复审产物使用其原生状态，例如 `NeedsReview`；对不再适用证据使用 `Expired`。
6. 保留旧编号、原始状态、证据和后继关系，不删除历史。
7. 明确恢复当前状态所需的评审、重新实现、重新执行或授权。
8. 重新评估受影响阶段门和交接包。

## 默认影响矩阵

| 变化来源 | 默认检查对象 |
| --- | --- |
| 代码、契约、配置、迁移、部署或运行事实 | 相关 `CTXF/CTXP`、关联 `CTXG`、父 `CTX` 聚合状态及引用它们的下游产物 |
| `REQ/RULE/AC` | `DEC/MOD/FLOW`、`DET/DDEC`、`IMP`、`TSC/TC`、`EVD/GATE`、发布范围 |
| `DEC/MOD/FLOW` | `DET/DDEC`、实现、跨模块测试、发布和运行手册 |
| `DATA/API/EVT/JOB/CFG` | 实现、迁移、调用方、消费者、契约测试和兼容测试 |
| `API/EVT/OpenAPI/AsyncAPI/Proto/SDL` | 相关 `FIA`、前端消费场景、联调检查、兼容说明和引用该语义的测试/证据 |
| `FIA` 消费语义、范围或版本 | 前端对接实现、联调清单、消费侧测试预期和相关验证证据 |
| `DDEC` | `IMP`、相关 `AUT`、`DVAL` 和执行证据 |
| 代码、依赖或配置 | `BUILD`、`REV`、相关测试证据、质量门禁和发布产物 |
| `REV` 结论或评审范围 | `IMP Reviewed/Integrated`、验证范围、质量门禁和发布就绪 |
| `TSC/TC` 预期 | `AUT`、执行批次、旧验证证据和门禁聚合 |
| `TENV/TCOND` | 执行就绪、环境相关证据和可推广结论 |
| 发布产物或迁移脚本 | 发布门禁、部署记录、观察结论和回滚能力 |
| `INC/RCA` | 需求、设计、永久修复、回归测试和运行手册 |

## 强制失效条件

以下变化会使相关上下文进入 `PotentiallyStale` 或 `Stale`：绑定版本变化；关键实现、契约、配置、生成源、迁移或
部署发生语义变化；运行事实超出记录环境或新鲜度；索引与目标仓库或版本不匹配。上下文失效不自动说明业务需求或
目标设计失效，但引用该上下文的结论必须重新评估。

子制品变化时按 `dev-ctx` 的聚合规则判断父包状态：非关键子制品失效只影响引用分支；关键性未知或关键子制品进入
`PotentiallyStale/Stale` 时，父 `CTX` 先进入 `PotentiallyStale`。失效通知必须使用标准 `Prepared HOF`，并通过
`consumer_refs` 或统一制品索引定位已知消费者；无法证明消费者覆盖完整时保留该未知边界。

出现以下任一情况时，相关执行证据不能继续视为有效：

- 被测代码、契约或关键配置不再属于证据记录的版本。
- 预期结果或判定依据发生实质变化。
- 数据迁移改变了被验证的数据语义或状态。
- 环境差异会影响结论且未重新证明等价性。
- 自动化断言、夹具或依赖替身存在影响结果的变化。
- 证据超过明确的新鲜度期限或被责任方撤销。

## 不得机械传播

- 文本格式、章节顺序、注释或无语义重构不自动使全部下游失效。
- “代码未修改”不能单独证明没有数据、配置、契约或运行影响。
- “现有测试通过”不能阻止需求或设计变化触发复审。
- 无法确认影响时保持 `PotentiallyAffected` 并形成交接，不虚构安全结论。
