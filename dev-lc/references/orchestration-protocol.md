# 调度协议

本协议供调度 Agent 或承担同等职责的主会话按需读取。它定义如何使用 Dev Skills 协调多阶段工作，不改变
`artifact-contract.md`、`lifecycle-state-model.md`、`handoff-contract.md` 和 `invalidation-rules.md` 的语义。

所有调度中间状态遵循 `external-state-contract.md`，保存在项目外部。项目目录只接收用户明确确认的最终产物。

## 1. 何时使用调度

满足以下任一条件时，适合使用调度 Agent：

- 用户要求端到端交付、跨模块改造、系统集成、数据迁移、架构迁移、事故闭环或发布到运行的完整链路。
- 工作预计跨越三个或更多专业 Skill。
- 多个阶段需要并行推进、版本对齐、失效传播或反复交接。
- 需要从已有 `CHG/HOF/LCV` 恢复中断的工作。

以下情况优先直接调用专业 Skill：

- 请求只涉及一个明确阶段。
- 两个阶段之间依赖简单，不需要并行、失效传播或正式交接治理。
- 用户只要求解释、检查或生成一个局部产物。

调度是按需能力，不是所有变更的前置门。

## 2. 运行模式

### 路由模式

用于只读评估，或宿主没有提供 `Agent` 工具、已达到派生深度/并发限制。输出路线、最小任务包、阻塞和授权缺口，不假装已经执行专业阶段。

### 协调模式

仅在用户已要求实际推进、平台允许派生 Agent 且目标仍在授权范围内时使用。调度 Agent 将专业任务交给独立执行上下文，自己只维护依赖、状态和结果收敛。

协调模式分为：

- `session-coordinate`：只有当前会话和原生子代理可用，不持久化控制对象；适合一次会话内完成且无需恢复的工作。
- `durable-coordinate`：同时具有符合外置状态契约的状态服务，允许版本化保存和恢复 `CHG/HOF/LCV/WIT`。

Codex 或 Claude Code 提供原生子 Agent 时，调度器应使用最浅的充分任务树；达到限制时退回路由模式，不能把派生失败解释为专业阶段失败。平台差异读取 [调度映射](../../dev-orch/references/platform-mapping.md)。

不得因为用户要求“全流程”而推定发布、生产、真实数据或外部系统变更已获授权；这些动作在到达对应边界时仍需精确授权。

## 3. 状态重建

每次启动或恢复时按以下顺序重建状态：

1. 复用权威 `CHG`；没有正式编号时使用临时编号并明确其局部性。
2. 读取 `LCV` 中登记的路线、阶段门、产物版本、证据、阻塞和失效状态。
3. 读取未关闭 `HOF`，区分 `Prepared`、`Accepted`、`Rejected` 和已被替代的交接。
4. 核对专业产物信封及其来源版本，不从聊天摘要推定正式状态。
5. 发现输入版本变化时，先执行失效分析，再决定哪些任务可继续。

存在外置状态服务时首先调用 `workspace_resolve` 获取 `workspace_id`。状态服务不可用时不在项目中创建替代状态目录；
需要可恢复状态则使用 `route-only`，无需恢复且用户要求当前会话执行时可使用 `session-coordinate`。

聊天内容可以提供线索，不能替代正式产物、仓库事实、验证证据或授权记录。

## 4. 路由算法

1. 分类变更类型和风险：新建、存量变更、规则调整、缺陷、集成、契约、迁移、下线、事故或运行改进。
2. 识别可复用且仍有效的基线；存量实现或影响范围未知时加入 `dev-ctx`。
3. 选择最短充分路线，不机械串行执行全部 Skill。
4. 对每个节点登记输入版本、进入条件、输出、责任模块和停止条件。
5. 仅当节点没有未满足的硬依赖、使用同一有效输入版本且不会并发修改同一责任对象时并行。
6. 专业结果返回后先校验产物和证据，再准备 `HOF`；接收方没有确认时保持 `Prepared`。
7. 发生失败、拒绝或输入变化时，沿追踪链标记影响并重新计算未完成路线。

当宿主支持命名 Agent 的续接和停止时，后续修正优先恢复原 Agent 上下文，不重复创建同一责任任务；输入已失效的运行分支应先停止，再按新版本重新派发。

常见但非强制的并行关系：

- `dev-test` 可在需求基线形成后开始，并随 HLD、LLD 和实现逐步细化。
- 存在前端消费方时，`dev-fia` 在适用 `API/EVT` 或机器契约达到可引用版本后开始；它可以与实现和测试细化并行，
  但上游契约变化必须先触发 `FIA` 失效检查。
- 不修改同一文件或契约的多个实现任务可以并行。
- `dev-cr` 必须基于明确的实现候选版本；`dev-val` 必须区分实现自测与独立验证证据。
- `dev-rel` 依赖适用门禁和发布授权；`dev-ops` 的发布后观察不等于事故处理。
- `dev-fia` 的 `Ready` 只表示联调输入就绪，不表示前端实现、接口实现、测试或验收通过。

## 5. 专业任务包

每个派发任务至少包含：

| 字段 | 内容 |
| --- | --- |
| 变更 | `CHG`、目标和变更类型 |
| 任务 | `WIT`、目标专业 Skill、任务目标和责任边界 |
| 输入 | 产物编号、版本、事实来源和适用范围 |
| 范围 | 包含项、非范围、允许修改的对象 |
| 约束 | 保留行为、兼容要求、风险和授权边界 |
| 输出 | 期望产物、证据、验证方式和 `HOF` 目标 |
| 控制 | 进入条件、停止条件、阻塞上报条件 |

只传递完成任务所需的最小上下文。接收方必须按其专业 Skill 工作，不能由调度 Agent 预写专业结论。

每个 `WIT` 必须带稳定工作项编号、输入指纹、尝试次数、归属对象和当前 Agent ID。返回结果的输入指纹与当前版本不一致时不得接收。

## 6. 结果收敛

调度 Agent 对返回结果只做控制面检查：

- 产物身份、版本、来源、范围和状态是否明确。
- 预期验证是否有证据，失败是否已分类。
- 是否产生新的风险、未决项、失效关系或授权缺口。
- `HOF` 是否完整且状态没有越权提升。
- 下游任务的输入版本是否仍然有效。

内容正确性、设计接受、评审结论、质量门、风险接受和发布批准仍由对应责任模块或人员决定。

## 7. 失败、恢复与停止

- 任务失败或超时时，保留已取得证据，标记受影响分支为阻塞；不要无界重试。
- 交接被拒绝时，保留拒绝原因和被替代关系，返回产生缺口的最近责任阶段。
- 输入失效时，不删除旧产物；登记 `NeedsReview/Expired` 等原生状态和恢复条件。
- 用户撤回范围、授权不足、专业结论相互冲突或生产边界未获授权时停止相关分支，其他独立分支可继续。
- 完成条件是适用路线均有可验证结果、开放交接和阻塞已处理，并且正式确认来自有权责任方；调度 Agent 不能自行宣布这些确认。
