# 复杂度与拆分治理

## 目的与边界

本规则统一约束 Dev Skills 中的过度设计和过度拆分。它不要求组件数量最少，也不允许为了“简单”合并本应独立的业务、数据、权限、事务、失败、部署或恢复边界。`dev-lc` 维护规则，专业 Skill 在自己的产物和结论中应用；不新增独立产物、阶段门或审批角色。

## 判定定义

- **必要复杂度**：为落实有效需求、已接受设计、当前实现约束或有证据风险而必须承担的结构与机制成本。
- **过度设计**：新增抽象、层、模块、服务、中间件、依赖、通用能力或扩展点，但无法追踪到当前有效需求、设计决策、实现约束或已识别风险。
- **有效拆分**：拆分后的单元具有至少一个可独立判断的边界，并降低耦合、隔离风险或形成明确责任。
- **过度拆分**：拆分单元没有独立职责或边界，却增加调用、映射、状态同步、追踪、测试、发布、恢复或交接成本。

文件数、类数、行数、服务数、`DET/IMP/TC/WIT` 数量只能作为调查信号，不能单独证明过度设计或过度拆分。

## 证据规则

新增机制、抽象或拆分至少应具有一种可复核依据：

- 独立业务职责、输入输出或可观察结果；
- 独立数据权威、权限或安全边界；
- 不同事务、状态、副作用、失败或恢复边界；
- 独立部署、版本兼容、迁移、回滚或验证要求；
- 已确认的性能、容量、可靠性或合规约束；
- 明确的责任团队或并行交付边界，且拆分收益大于协作成本。

“以后可能需要”“设计模式要求”“工具可以生成”“编号更整齐”或个人偏好不是充分依据。未来扩展只有成为有效需求、已接受决策或当前证据支持的演进约束时才能作为依据。

## 最低充分决策

1. 先建立满足当前范围和保持项的最简单可行基线。
2. 新增每个机制或单元时，说明它解决的当前问题、依据、增加的成本以及不采用更简单方案的理由。
3. 现有模式、模块、工具或依赖能够满足目标时优先复用；不要为局部变化建立平行事实源或通用框架。
4. 只有边界可独立说明、实现、失败、恢复、部署、负责或验证时才拆分；连续步骤和相同边界默认保持在同一单元。
5. 临时适配层、兼容层、双轨流程和过渡单元必须具有适用范围、退出条件和删除责任。
6. 不为减少数量而合并不同数据权威、事务、权限、失败或发布边界；必要复杂度必须保留并说明依据。

## 分阶段应用

| Skill | 应用范围 |
| --- | --- |
| `dev-hld` | 系统、服务、模块、中间件、数据权威和部署边界 |
| `dev-lld` | `DET/DDEC`、类与接口、处理层、算法表达和实施任务拆分 |
| `dev-impl` | 实际代码结构、依赖、适配层、配置、迁移及 `IMP` 拆分 |
| `dev-cr` | 独立检查候选中的复杂度依据、拆分收益和新增成本 |
| `dev-test` | 场景、用例、数据、夹具和自动化层次的必要拆分 |
| `dev-orch` | 阶段、任务包、Agent、交接和持久化控制面的必要性 |

`dev-req` 只保持需求必要性、单一性和实现中立，不决定技术拆分。`dev-val/dev-rel/dev-ops` 可以记录复杂度造成的验证、发布或运行风险，并交回对应设计或实现责任方，不自行重构方案。

## 评审与严重度

- 仅增加理解、修改或维护成本，且不影响当前正确性与交付：通常为 `P2`。
- 显著增加正确性、事务、并发、兼容、安全、验证、发布或运行风险：按实际影响评为 `P1`。
- 只有底层影响可能造成越权、不可恢复数据损坏、破坏性兼容或范围不可判断时才评为 `P0`；不得仅凭“过度设计”标签升级。

发现应说明具体位置、缺失或不足的依据、额外成本、受影响边界、最小整改目标和验证要求。复杂度具有充分依据时不得为了追求更少组件而制造问题。

## 产物记录

不创建新的复杂度产物。概要选择记录在 `DEC/MOD`，详细机制和拆分记录在 `DET/DDEC`，实际实现记录在 `IMP/BUILD`，独立发现和结论记录在 `REV`，责任转移使用 `HOF`。旧结论因范围、机制或拆分变化失效时，继续使用现有失效传播规则。
