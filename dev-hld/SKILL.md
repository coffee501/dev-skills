# Dev HLD

将已确认的需求基线转化为系统级设计基线：说明系统边界、模块职责、协作方式、数据归属、关键 `DEC`、核心 `FLOW`、风险和必要 `VAL`，并为 `dev-lld` 和 `dev-test` 提供输入。

## 职责边界

只回答“系统如何拆分、各部分如何协作、为什么这样设计”。目标、范围、规则、状态、数据口径、权限或验收缺失时返回 `dev-req`，不要用设计假设替代业务决策。

默认不输出：数据库字段、类型、索引和约束；接口路径、完整参数、错误码和字段级协议；类级结构、函数、算法、代码和模块内部步骤；具体锁、版本号、幂等键、幂等存储和补偿实现；日志字段、告警表达式、采集实现和运行处置；完整测试步骤、测试数据和自动化脚本；生产发布、灰度、回滚和运维操作。

字段级、接口级、类级或算法级方案交给 `dev-lld`；完整测试用例和自动化脚本交给 `dev-test`；生产发布与运行处置交给套件外责任流程。

## 生命周期接入

复用已有 `CHG`；没有权威编号时使用临时 `CHG-PENDING-001`。概要设计记录版本、来源、适用范围和关联需求，不改变上游编号。

需要正式编号或追踪时读[产物协议](../dev-orch/references/artifact-contract.md)，正式交接时读[交接协议](../dev-orch/references/handoff-contract.md)，输入变化时读[失效传播规则](../dev-orch/references/invalidation-rules.md)，评估阶段门时读[状态与阶段门](../dev-orch/references/lifecycle-state-model.md)。共享协议不可用时可独立完成诊断、设计、评审和拆分，但只能使用本地临时标识；不得宣称正式 G2、标准 HOF 已确认。

## 输入可信度

优先读取需求基线、关联需求编号、现有架构和代码、部署资料、接口及数据库现状、历史设计决策和当前对话结论。标记信息为已确认、合理推断、待确认、存在冲突或已废止。

可信度顺序：当前明确确认、正式需求基线、有效设计决策、现有系统事实、历史资料、行业惯例。现有系统是约束和现状，不自动等于目标设计。不得编造性能指标、容量、数据规模、外部能力、技术栈约束或合规要求。

## 模式与档位

选择一种工作模式：设计诊断、完整设计、增量完善、设计评审、详细设计拆分。设计评审只输出问题、证据、影响和建议；详细设计拆分面向 `dev-lld` 输出模块任务、输入和约束。

选择最低但足够的档位：轻量设计合并章节完成闭环；标准设计展开主骨架和有依据的质量约束；生产设计只在分布式、关键业务、复杂迁移或严格合规时展开质量、演进、验证和下游输入。不要把完整目录当作检查表；缺少依据时记为待确认，存在核心需求缺口时保持草案。

- 已有系统、功能变更、替换、迁移、合并、拆分或下线：读 [references/brownfield.md](references/brownfield.md)。
- 已有功能变更、业务规则调整、系统集成、数据迁移、功能下线或架构迁移：读 [references/compatibility-checklist.md](references/compatibility-checklist.md)。
- 局部架构问题：只读直接相关参考。

## 存量与兼容

存在代码、数据库、接口、部署或运行中的旧版本时，先建立 As-Is 证据基线，再设计 To-Be、Gap、Impact、Transition 和 Verification。代码只能证明当前可能实现了什么，不能单独证明该行为是正确需求或未来必须保留。

除纯新建系统外，都要检查兼容性。业务兼容覆盖角色、规则、状态、结果、历史数据和在途流程；未确认问题返回 `dev-req`。技术兼容覆盖接口、事件、数据格式、版本、部署和运行环境，由 `dev-hld` 定策略，再交给 `dev-lld`。

GitNexus 可用且索引新鲜时可辅助定位聚类、流程、符号关系、调用路径和影响半径；不可用或过期时回退到代码搜索、入口追踪、测试、配置、数据库和部署资料。不得把聚类名当作业务模块，也不得把“未发现路径”解释为“不存在该行为”。

## 主流程

1. 核对目标、范围、非范围、核心需求、约束和关联需求编号。
2. 识别需求类型、工作模式和输出档位，读取适用参考。
3. 有存量实现时先建立 As-Is 和兼容影响，再建立目标系统上下文。
4. 区分业务决策与架构决策；业务问题返回需求，架构候选方案记录影响。
5. 划分 `MOD`，明确职责、非职责、数据所有权和依赖方向。
6. 梳理影响系统协作的正常、异常、恢复和失败传播 `FLOW`。
7. 建立领域对象、关系、核心数据集合、接口语义和数据生命周期。
8. 按依据定义跨边界一致性、安全、性能、可用性和运行边界。
9. 汇总风险、`VAL`、待确认事项和详细设计任务。
10. 检查追踪、图文一致性、职责边界、过度设计和基线条件。

主线：目标与约束 → 系统边界与架构 → 关键 `DEC` → `MOD` 与数据归属 → `FLOW` 与接口协作 → 适用的一致性、安全和质量约束 → 兼容演进 → 验收映射、`VAL` 与交接。

## 硬约束

- 改变角色权限、业务资格、业务状态、业务结果、时间规则或数据含义的选择属于需求决策，只能作为待确认业务问题及候选影响。
- `DEC` 只记录显著影响系统边界、模块划分、数据归属、协作方式、一致性、安全、核心存储、部署形态或迁移路线的决策。
- 最小追踪链：`REQ/RULE/AC → 适用的 DEC/MOD/FLOW/质量约束 → VAL 或下游交接`。
- `VAL` 表示设计可行性或关键风险验证，不替代业务 `AC`，也不展开为完整测试用例。
- 事务、一致性、异步、缓存、限流、熔断、消息队列、分布式事务等机制必须有跨边界业务结果或明确风险依据。
- 安全始终最低限度检查身份主体、信任边界、操作权限、数据权限与隔离、敏感数据分类。
- 性能、容量、恢复、容灾、合规和外部能力必须注明来源；没有依据时记录待确认。
- 日志、监控、鉴权等横切关注点只有在拥有独立能力、数据、生命周期或责任团队时才划为模块。

## 基线与交接

标记“概要设计基线”前，必须确认：目标、范围、非范围、关键约束、系统边界、模块职责和依赖方向明确；核心数据有权威方；核心流程、状态和失败后的业务结果明确；关键 `DEC` 至少为 `Accepted`，决定可行性的重大风险有 `VAL`，验证通过前不得标记 `Validated`；安全最低检查完成；影响架构的关键 `AC` 已有关联设计响应；关键内容可沿需求、验收、决策、模块、流程和适用 `VAL` 追踪；不存在未解决架构 P0；后续详细设计任务已按模块拆分。存量变更还必须明确 As-Is、To-Be、Gap、调用方、消费者、历史数据、在途业务、共存、迁移、回退和验证原则。

向 `dev-lld` 交接模块边界、职责、领域对象、数据归属、接口语义、事务和一致性原则、安全边界、性能容量目标、部署约束、关键 `DEC`、关联 `AC`、风险及详细设计任务。

向 `dev-test` 交接关联 `REQ/RULE/AC`、核心场景、跨模块流程、关键状态和数据变化、失败语义、质量指标、设计验证目标，以及需要覆盖的兼容、迁移和容灾场景。

最终质量检查读取 [references/review-checklist.md](references/review-checklist.md)，删除无依据技术清单、重复结论和空章节，并确认没有把 HLD 扩展成 LLD、测试或发布运维方案。
