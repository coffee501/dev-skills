# Dev HLD

将已确认的需求基线转化为边界清楚、决策有依据、职责可追踪、风险可验证且能够指导详细设计的系统级设计基线。

## 接入 Dev 生命周期

跨阶段、存量改造、迁移、下线或架构变化复用已有 `CHG`；没有权威编号时使用临时 `CHG-PENDING-001`。概要设计产物记录版本、来源、适用范围和关联需求，不自行改变上游编号。

需要统一产物和追踪时读取 [产物协议](../dev-lc/references/artifact-contract.md)；形成详细设计或测试设计交接时读取 [交接协议](../dev-lc/references/handoff-contract.md)；需求、决策、边界或现有实现变化时读取 [失效传播规则](../dev-lc/references/invalidation-rules.md)。阶段门和基线含义遵循 [状态与阶段门](../dev-lc/references/lifecycle-state-model.md)，概要设计基线不代表实现或验证通过。

共享协议不可用时仍可独立完成概要设计诊断、设计、评审和详细设计拆分，使用本地临时标识并保留来源、范围、风险和
证据；不得宣称正式G2、全局编号或标准HOF已经确认，也不因治理模块缺失而虚构状态。

## 保持职责边界

聚焦系统整体如何拆分、各部分如何协作，以及架构为什么这样设计。

默认不要输出：

- 数据库字段、字段类型、索引和完整性约束
- 接口路径、完整参数、错误码和字段级协议
- 类、函数、算法、代码和模块内部处理步骤
- 具体锁、版本号、幂等键和幂等存储实现
- 日志字段、告警表达式和监控采集实现
- 完整测试步骤、测试数据和自动化脚本

发现目标、范围、业务规则、状态、数据口径、权限或验收要求缺失时，将问题返回 `dev-req`，不要用设计假设掩盖需求缺口。需要字段级、接口级、类级或算法级方案时，将任务交给 `dev-lld`。只定义验证目标和通过条件，将完整测试用例交给 `dev-test`。

凡是会改变参与者权限、业务资格、业务状态、业务结果、时间规则或数据含义的选择，都属于需求决策。可以列出候选项及其架构影响，但不得替业务方选定结论或将其登记为最终设计决策。

## 建立可信输入

优先读取需求基线、关联需求编号、现有架构和代码、部署资料、接口及数据库现状、历史设计决策和当前对话结论。

区分：

- **已确认**：可以写入正式设计。
- **合理推断**：可以形成候选方案，不得伪装成项目事实。
- **待确认**：缺少依据或需要负责人决策。
- **存在冲突**：来源之间不一致，列出来源、影响和处理责任。
- **已废止**：已被新决策替代，仅保留追踪关系。

按以下顺序判断可信度：当前明确确认的结论、正式需求基线、有效设计决策、现有系统事实、历史资料、行业惯例。把现有系统视为约束和现状，不自动视为目标设计。不得编造性能指标、容量、数据规模、外部能力、技术栈约束或合规要求。

存在代码、数据库、接口、部署或运行中的旧版本时，先建立存量实现证据基线。代码能够证明当前可能实现了什么，不能单独证明该行为是正确需求、生产中必然发生或未来必须保留。

## 选择工作模式

| 模式 | 使用条件 | 默认输出 |
| --- | --- | --- |
| 设计诊断 | 输入粗略、冲突或可能无法进入设计 | 需求理解、缺失与冲突、主要风险、完整度、三至五个最高优先级问题 |
| 完整设计 | 用户要求完整文档或信息基本充分 | 所选档位下全部适用章节、图、决策、风险和后续任务 |
| 增量完善 | 用户补充结论或修改约束 | 新增、修改、废止内容及受影响章节、决策、图、追踪链和下游任务 |
| 设计评审 | 用户要求检查已有设计 | 按严重度排序的问题、证据、影响、修改建议和待确认事项，不重写全文 |
| 详细设计拆分 | 概要设计已基本稳定 | 按模块形成 `dev-lld` 任务，明确输入、约束、关联需求和未决问题 |

存在未解决的核心需求缺口时，将文档标记为“概要设计草案”。

## 识别需求类型

在选择输出档位前识别主类型和可能的次类型：

| 类型 | 兼容性处理 |
| --- | --- |
| 新建系统 | 默认不进入存量兼容检查；存在既有调用方、共享数据或部署约束时除外 |
| 已有功能变更 | 自动进入兼容性分析 |
| 业务规则调整 | 自动检查历史数据、在途业务和新旧规则适用范围 |
| 系统集成 | 自动检查双方契约、数据权威、失败语义和版本兼容 |
| 数据迁移 | 自动检查历史数据、校验、共存、切换和回退 |
| 功能下线 | 自动检查调用方、消费者、数据保留、替代能力和退出条件 |
| 架构迁移 | 自动检查新旧能力共存、流量切换、部署和运行兼容 |

除纯新建系统外，读取 [references/compatibility-checklist.md](references/compatibility-checklist.md) 并输出兼容结论。多个类型并存时分别检查，不以主类型掩盖次类型风险。

## 选择输出档位

| 档位 | 典型条件 | 展开原则 |
| --- | --- | --- |
| 轻量设计 | 单一应用、边界简单、外部依赖少、非关键内部系统 | 合并相关章节，完成目标、架构、模块、流程、数据、接口和风险闭环；不照搬完整目录 |
| 标准设计 | 多模块、存在外部系统或明确生产约束 | 完成主骨架，展开适用的决策、一致性、安全、部署和运维内容 |
| 生产设计 | 分布式、关键业务、高并发、高可用、复杂迁移或严格合规 | 展开所有有依据的生产与条件章节，并形成验证和演进方案 |

用户指定档位时以用户要求为准；否则根据证据选择最低但足够的档位。不要把完整目录当作必须填满的检查表。

轻量设计优先使用七个以内的一级章节，将安全和运维最低原则并入相关章节。日志、监控、鉴权等横切关注点只有在拥有独立能力、数据、生命周期或责任团队时才划分为模块。

## 按需读取参考文件

- 生成或重构完整概要设计、确定章节结构或绘图时，读取 [references/outline.md](references/outline.md)。
- 评审现有设计或执行最终质量检查时，读取 [references/review-checklist.md](references/review-checklist.md)。
- 分析已有系统、功能变更、兼容、迁移、替换或下线时，读取 [references/brownfield.md](references/brownfield.md)。
- 已有功能变更、业务规则调整、系统集成、数据迁移、功能下线或架构迁移时，读取 [references/compatibility-checklist.md](references/compatibility-checklist.md)。
- 只回答局部架构问题时，不必读取与问题无关的参考文件。

## 处理已有实现

读取 [references/brownfield.md](references/brownfield.md)，按以下主线分析：

> As-Is 现有实现 → To-Be 目标设计 → Gap 差异 → Impact 影响 → Transition 过渡 → Verification 验证

存在符合共享资格规则的 `Eligible CTX` 及其引用的 `CTXF/CTXP/CTXG` 时优先复用，并检查其新鲜度、证据边界和当前设计问题所需
的最小充分性。只对缺失、冲突或潜在过期部分做定向核验，不重复全量发现。没有可用 `CTX` 时可以为当前设计建立
最小只读As-Is证据；若上下文需要被多个阶段复用、仓外信息缺失或缺口阻塞设计，形成面向 `dev-ctx` 的 `Prepared HOF`。
`dev-hld` 不创建或改写 `CTX` 编号和状态。

如果 GitNexus 已可用并已索引目标仓库，优先用它定位功能聚类、执行流程、符号关系、调用路径和影响半径；先检查仓库上下文与索引新鲜度，再使用适合的 GitNexus 工作流。索引陈旧、缺少目标仓库或工具不可用时，回退到代码搜索、入口追踪、测试、配置、数据库和部署资料检查，不得阻塞分析。

所有存量结论都要区分实现证据、架构推断和业务待确认，并尽可能附文件、符号、流程、配置或运行证据。不得把 GitNexus 聚类名称直接当作业务模块，不得把调用关系直接当作业务职责，也不得把“未发现路径”解释为“系统不存在该行为”。

## 执行设计流程

1. 核对目标、范围、非范围、核心需求、约束和关联需求编号。
2. 识别需求类型，选择工作模式和输出档位，读取适用参考文件。
3. 存在已有实现时先建立 As-Is 基线和兼容影响；再建立目标系统上下文、责任边界、总体架构和外部系统关系。
4. 区分业务决策与架构决策；将业务问题返回需求，比较架构候选方案并记录关键决策。
5. 划分模块，明确职责、非职责、数据所有权和依赖方向。
6. 选择影响系统协作和架构的核心场景，梳理正常、异常和恢复流程。
7. 建立领域对象、关系、核心数据集合、接口语义和数据生命周期。
8. 根据跨边界一致性、安全、性能、可用性和生产约束，定义必要的总体策略。
9. 汇总风险、验证计划、待确认事项和详细设计任务。
10. 执行追踪、图文一致性、边界和基线完成条件检查。

持续检查主线：

> 目标与约束 → 系统架构 → 关键决策 → 模块职责 → 核心流程 → 领域与数据 → 接口依赖 → 一致性、安全和性能 → 部署运维 → 风险与后续设计

## 管理关键设计决策

只记录会显著影响系统边界、模块划分、数据归属、协作方式、一致性、安全、核心存储、部署形态或迁移路线的决策。

记录前先检查该选择是否改变业务角色、资格、规则、状态、结果、时间或数据语义；如果会改变，则只记录为待确认业务问题及候选方案影响，不创建最终 `DEC` 结论。

为关键决策分配稳定编号 `DEC-001`。每项决策至少包含：

| 内容 | 说明 |
| --- | --- |
| 设计问题 | 需要解决什么 |
| 关联需求 | 为什么需要决策 |
| 候选方案 | 有哪些可行方案 |
| 最终选择 | 采用什么 |
| 选择依据 | 为什么选择 |
| 代价和限制 | 放弃了什么 |
| 风险 | 可能出现什么问题 |
| 验证方式 | 如何证明设计可行 |

“核心技术选型”只展示选型摘要、使用范围和关联 `DEC` 编号；不要与决策记录重复维护候选方案和取舍。新信息改变已确认决策时，将原决策标记为已废止，创建或引用替代决策，并同步更新受影响章节、图、追踪链和下游任务。

管理决策状态：

> `Proposed → Accepted → Validated`，或从 `Accepted` 转为 `Superseded` / `Deprecated`

- **Proposed**：候选方案，尚未正式选择。
- **Accepted**：已经选择，但不代表可行性已验证。
- **Validated**：关键假设和验证条件已经通过。
- **Superseded**：已被另一项决策替代，引用替代 `DEC`。
- **Deprecated**：仍可能暂时存在，但已计划退出并具有退出条件。

概要设计基线中的关键决策至少达到 `Accepted`；决定可行性的重大风险必须具有 `VAL`，通过前不得标记为 `Validated`。

现有代码或部署形态可以形成约束、兼容风险或候选依据，但不能仅因“已经这样实现”就确定目标决策。保留现状时说明保留依据；改变现状时说明影响、过渡和验证方式。

## 建立最小追踪链

对关键内容建立：

> `REQ-001 → DEC-001 → MOD-001 → FLOW-001 → VAL-001`

- `REQ` 来源于需求基线。
- `DEC` 表示关键设计决策。
- `MOD` 表示承担职责的模块。
- `FLOW` 表示跨角色或跨模块场景。
- `VAL` 表示设计验证项或验收约束。

简单项目只为关键需求、决策和流程编号，不要机械编号所有段落。修改任一节点时检查相邻节点是否仍然一致。

对存量变更建立影响链：

> `REQ-CHG-001 → 受影响 DEC → 受影响 MOD → 受影响 FLOW → 数据与接口影响 → 兼容策略 → VAL 回归验证`

业务兼容覆盖角色、规则、状态、结果、历史数据和在途流程；其中未确认问题返回 `dev-req`。技术兼容覆盖接口、事件、数据格式、版本、部署和运行环境，由 `dev-hld` 设计总体策略，再交给 `dev-lld` 实现。

## 控制条件设计

- **事务与一致性**：只在业务结果跨越模块、存储、进程或外部系统，或存在重复操作、补偿、对账和不一致窗口时展开。普通本地事务不要扩展为分布式设计。
- **安全**：始终最低限度检查身份主体、信任边界、操作权限、数据权限与隔离、敏感数据分类；认证产品、加密算法、审计和合规细节按依据展开。
- **性能与可用性**：只根据明确指标、容量、并发、恢复或容灾约束展开；没有依据时记录待确认项。
- **异步协作**：先说明为何需要异步、事件业务含义和失败影响，再决定是否使用消息队列；不要让目录诱导技术选型。
- **部署与运维**：生产系统说明运行单元、网络边界、发布、回滚、监控和人工处置原则；概念验证只保留必要环境和运行边界。

不得为了目录完整而引入缓存、消息队列、分布式事务、限流、熔断或其他技术机制。

## 管理核心图

把系统架构图、模块划分图、核心业务流程图、关键时序图、概念或逻辑 ER 图、部署架构图作为候选图集。仅在图能明显提升理解时生成，优先使用 Mermaid，并确保图与正文中的名称、边界、方向、状态和决策一致。具体生成条件见 [references/outline.md](references/outline.md)。

## 检查概要设计基线

只有同时满足以下条件，才标记为“概要设计基线”：

- 目标、范围、非范围和关键约束明确。
- 系统边界、模块职责和依赖方向明确，不存在明显职责重叠或空缺。
- 核心数据具有权威方，跨模块写入和引用原则明确。
- 核心流程、状态和失败后的业务结果明确。
- 重大决策具有依据、代价、风险和验证方式。
- 适用的安全、性能、部署和运维约束已经识别。
- 关键内容可以沿需求、决策、模块、流程和验证项追踪。
- 不存在未解决的架构 P0 问题。
- 后续详细设计任务已经按模块拆分。
- 对存量系统，As-Is、To-Be、Gap、受影响调用方和数据、兼容期、迁移、回退及验证原则已经明确。
- 已识别受影响调用方和消费者，历史数据与在途业务处理规则明确。
- 新旧版本共存规则明确，不兼容变更具有迁移方案。
- 回滚后的数据和状态仍可继续处理，或已明确不可逆变化的前向修复原则。
- 每项重大兼容风险至少关联一个 `VAL` 验证项。

不满足条件时保持“概要设计草案”，但仍输出当前能够确认的内容和阻塞项。

## 形成下游输入

向 `dev-lld` 提供模块边界、职责、领域对象、数据归属、接口交互语义、事务和一致性原则、安全边界、性能和容量目标、部署约束、关键决策、风险及详细设计任务。

向 `dev-test` 提供关联需求、核心场景、跨模块流程、关键状态和数据变化、失败语义、质量指标、设计验证目标及需要覆盖的兼容、迁移和容灾场景。

将未解决的业务目标、规则、状态、数据口径、权限和验收问题返回 `dev-req`，说明它们阻塞或影响的设计章节，不自行替代业务决策。

## 执行最终质量检查

读取 [references/review-checklist.md](references/review-checklist.md)，检查信息可信度、需求追踪、边界、决策、职责、数据归属、依赖、失败语义、图文一致性、条件设计依据和下游交接。存在已有实现时同步检查证据来源、兼容维度、过渡方案、旧调用方和历史数据。删除无依据的技术清单、重复结论和空章节。
