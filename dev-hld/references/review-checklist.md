## 问题严重度

- **P0**：阻塞系统边界、核心流程、数据权威、关键决策或设计可行性，无法安全进入详细设计。
- **P1**：影响一致性、安全、性能、部署、迁移、运维或重要验证，但不完全阻塞主体设计。
- **P2**：影响表达、追踪、维护性或后续优化。

## 1. 输入与追踪

- [ ] 目标、范围、非范围和成功条件来自有效需求或明确确认。
- [ ] 业务规则、状态、数据口径、权限和验收缺口已返回 `dev-req`。
- [ ] 已确认、合理推断、待确认、冲突和已废止内容没有混用。
- [ ] 现有系统行为被视为现状或约束，而不是自动视为目标设计。
- [ ] 关键设计内容能够沿 `REQ → DEC → MOD → FLOW → VAL` 追踪。
- [ ] 修改后的需求、决策、模块、流程和验证项保持相互一致。

## 2. 边界与决策

- [ ] 系统负责和不负责的内容明确。
- [ ] 系统、外部系统和团队之间的责任边界明确。
- [ ] 业务结果和核心数据具有明确责任方和权威方。
- [ ] 关键设计决策具有稳定 `DEC` 编号。
- [ ] 决策包含关联需求、候选方案、最终选择、依据、代价、风险和验证方式。
- [ ] 被替代的决策已标记为已废止并引用替代决策。
- [ ] 技术选型摘要引用决策记录，没有重复维护候选方案和取舍。
- [ ] 没有把个人偏好或行业惯例写成项目约束。
- [ ] 会改变角色权限、业务资格、状态、结果、时间规则或数据含义的问题已返回需求，没有被架构决策替代。

## 3. 模块、流程与数据

- [ ] 模块职责和非职责明确，没有明显重叠或空缺。
- [ ] 调用、数据和事件依赖方向明确，没有未解释的循环依赖。
- [ ] 模块说明保持在职责和协作层面，没有进入内部算法或逐步实现。
- [ ] 日志、监控、鉴权、配置等横切关注点没有在缺少独立能力、数据、生命周期或责任团队时被强行拆成模块。
- [ ] 核心流程覆盖正常、拒绝、异常、部分成功和恢复结果。
- [ ] 状态、数据变化位置和失败传播方式在流程与时序中一致。
- [ ] 核心领域对象、关系、归属、生命周期和关键状态明确。
- [ ] ER 图保持在概念或逻辑层面，没有伪装成物理数据库设计。
- [ ] 跨模块数据引用、写入和同步原则明确。

## 4. 接口与一致性

- [ ] 接口说明聚焦调用目的、交互语义、主要业务数据、失败语义和兼容原则。
- [ ] 没有越界输出完整参数、错误码和字段级协议。
- [ ] 异步协作先说明业务需要、事件含义和失败影响，再决定技术机制。
- [ ] 重试、超时、限流、隔离等治理策略具有具体风险依据。
- [ ] 事务边界与模块、存储和外部系统边界一致。
- [ ] 强一致、最终一致和不一致窗口具有业务依据。
- [ ] 幂等、补偿和对账只在存在相应场景时展开。
- [ ] 没有把普通本地事务升级为无依据的分布式事务设计。

## 5. 安全、性能与生产设计

- [ ] 最低检查了身份主体、信任边界、操作权限、数据权限与隔离、敏感数据分类。
- [ ] 认证产品、加密算法、审计和合规要求具有明确依据。
- [ ] 性能、容量、并发、恢复、RTO 和 RPO 指标均注明来源。
- [ ] 缓存、并发控制、限流、熔断、降级和容灾策略具有需求或风险依据。
- [ ] 生产设计说明必要的运行单元、网络边界、发布、回滚和人工处置原则。
- [ ] 迁移设计说明当前、过渡、目标状态和临时方案退出条件。
- [ ] 可观测性聚焦系统目标和责任边界，没有进入字段、表达式和采集实现。

## 6. 图文一致性

- [ ] 只生成能明显提升理解的图。
- [ ] 图中的系统、模块、对象和外部依赖名称与正文一致。
- [ ] 架构图、模块图和部署图的边界与方向一致。
- [ ] 流程图和时序图的参与者、顺序、状态、数据变化和失败传播一致。
- [ ] ER 图中的对象与领域模型和数据归属一致。
- [ ] 图中没有正文未说明的新组件、存储或机制。

## 7. 存量实现与兼容

- [ ] 已区分需求规定、代码实现、依赖方实际使用和历史偶然行为。
- [ ] 已识别需求类型；除纯新建系统外已经读取兼容性检查并确定检查范围。
- [ ] As-Is 结论具有文件、符号、流程、契约、配置、数据或运行证据，并注明置信度。
- [ ] GitNexus 仅作为可选实现证据源；使用时已检查目标仓库和索引新鲜度。
- [ ] GitNexus 聚类、调用和影响结果没有直接被写成业务模块、业务职责或业务正确性结论。
- [ ] 已建立 As-Is、To-Be、Gap、影响、过渡和验证关系。
- [ ] 业务兼容问题已返回 `dev-req`，技术兼容已经形成概要策略。
- [ ] 已建立 `REQ-CHG → DEC → MOD → FLOW → 数据与接口影响 → 兼容策略 → VAL` 影响链。
- [ ] 已检查业务行为、状态、数据、接口、事件、权限、配置、部署、运维和性能兼容的适用维度。
- [ ] 已识别旧调用方、历史数据、运行中业务、定时任务、批处理、报表、通知和人工入口。
- [ ] 过渡架构、新旧共存、兼容期、迁移顺序和临时方案退出条件明确。
- [ ] 回滚说明覆盖数据和状态不可逆变化，没有只写“支持回滚”。
- [ ] 关键决策状态正确区分 `Proposed`、`Accepted`、`Validated`、`Superseded` 和 `Deprecated`。
- [ ] 未识别调用方、历史数据规则、在途业务、共存、迁移、回滚或 `VAL` 覆盖时，文档保持草案状态。
- [ ] 工具未覆盖的动态调用、反射、运行时配置、外部仓库和手工流程已标记为未知或验证项。

## 8. 过度设计与职责越界

- [ ] 输出档位是满足项目证据的最低充分档位。
- [ ] 轻量设计合并了相关章节，没有照搬完整目录或生成超过必要数量的一级章节。
- [ ] 不适用章节已省略或简要说明依据，没有生成空章节。
- [ ] 没有无依据引入缓存、消息队列、分布式事务、限流、熔断或微服务。
- [ ] 没有编造指标、容量、数据规模、外部能力、技术栈或合规要求。
- [ ] 没有输出字段、索引、完整接口参数、类、函数、算法或代码。
- [ ] 没有把验证目标扩展为完整测试步骤和测试数据。
- [ ] 重复结论已经合并，技术选型与决策记录不存在双重事实源。

## 9. 基线与下游交接

- [ ] 目标、边界、模块职责、数据权威、核心流程和关键决策明确。
- [ ] 适用的安全、性能、部署和运维约束已经识别。
- [ ] 重大风险具有验证方式、通过条件和失败备选方案。
- [ ] 不存在未解决的架构 P0 问题。
- [ ] `dev-lld` 任务按模块明确设计对象、输入、约束、关联需求和未决问题。
- [ ] `dev-test` 获得场景、状态、数据变化、失败语义和验证目标。
- [ ] 业务缺口已返回 `dev-req`，没有被技术假设掩盖。
- [ ] 存量改造已将兼容、迁移、回退和历史数据约束交给对应下游任务。

## 10. 评审输出

按以下顺序组织评审结果：

1. 总体结论和当前档位。
2. P0、P1、P2 问题，逐项说明证据、影响和建议。
3. 需求追踪、边界、决策、职责、流程、数据和接口检查。
4. 适用的一致性、安全、性能、部署和运维检查。
5. 图文一致性和职责越界检查。
6. 待确认事项及其归属。
7. 存量系统的兼容、迁移、回退和未知证据范围。
8. 是否满足概要设计基线条件。

用户只要求评审时，不重写完整设计文档。
