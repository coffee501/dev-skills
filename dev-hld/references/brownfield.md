# 存量实现与兼容性分析

在已有系统、功能变更、替换、迁移、合并、拆分或下线场景中读取本文件。目标是从实现证据建立 As-Is 基线，再设计 To-Be、Gap、影响、过渡和验证；不要把代码现状自动写成业务需求或目标架构。完成证据基线后，读取 `compatibility-checklist.md` 判断必须保持的行为、兼容策略和基线阻塞项。

## 1. 分析原则

持续使用以下主线：

> As-Is 现有实现 → To-Be 目标设计 → Gap 差异 → Impact 影响 → Transition 过渡 → Verification 验证

- 把现有实现视为当前事实、约束和兼容对象，不自动视为正确需求。
- 区分需求规定行为、代码实现行为、依赖方实际使用行为和历史偶然行为。
- 对没有明确变更依据的外部可观察行为优先保持兼容，但不要据此掩盖缺陷或业务冲突。
- 对准备改变的行为说明依据、受影响对象、兼容期、迁移方式、回退限制和验证方法。
- 只在概要层描述原则和边界，把字段转换、脚本、适配代码和版本判断交给 `dev-lld`。

## 2. 证据层级

按来源标记每项存量结论：

| 类型 | 含义 | 可支持的结论 |
| --- | --- | --- |
| 业务确认 | 业务负责人或有效需求明确确认 | 目标规则和必须兼容的业务行为 |
| 运行证据 | 生产指标、日志、追踪、审计、真实数据或操作记录 | 实际发生的行为和使用强度 |
| 契约证据 | 对外文档、接口契约、事件规范、自动化验收或消费者测试 | 对外可观察兼容承诺 |
| 实现证据 | 代码、测试、数据库、配置、部署和 GitNexus 图谱 | 当前可能实现的路径、结构和依赖 |
| 架构推断 | 多项证据共同支持的归纳 | 候选模块、职责、数据流和风险 |
| 未知 | 当前材料无法证明 | 待确认问题或验证任务 |

发现冲突时同时保留来源和影响，不自行选择代码、文档或运行行为中的任一方作为结论。

每项重要结论尽量记录：证据类型、仓库、文件或资源、符号或流程、版本或提交、新鲜度、结论、置信度和待确认项。

## 3. GitNexus 辅助流程

GitNexus 是可选的代码事实提取工具，不是本 Skill 的硬依赖。可用时按以下顺序执行：

1. 仓库名称未知时使用 `list_repos` 定位已索引仓库；分页枚举直到找到目标，不猜测仓库名。
2. 读取 `gitnexus://repo/{name}/context`，确认路径、索引时间、提交和新鲜度。
3. 索引陈旧时优先更新索引；仓库内存在 `.gitnexus/run.cjs` 时可运行 `node .gitnexus/run.cjs analyze`。无法更新时标记图谱证据可能过期。
4. 理解架构和业务流程前读取适用的 `gitnexus-exploring` 工作流；评估变更影响前读取 `gitnexus-impact-analysis` 工作流。
5. 读取 `clusters` 和 `processes`，形成候选功能区域与执行流程，不直接把聚类名称写成业务模块。
6. 使用 `query` 搜索用户术语、状态、操作和业务对象，获得按流程分组的相关代码。
7. 对入口、核心服务、状态处理、数据访问和外部调用使用 `context`。
8. 使用 `trace` 验证入口到关键状态变化、数据写入或外部调用的最短路径；无路径时记录搜索边界，不证明行为不存在。
9. 对计划变更的核心符号使用 `impact`；对当前 Git 变更使用 `detect_changes`，识别深度 1～3 的影响和置信度。
10. 只有需要函数内部控制或变量流时才使用 `pdg_query`；确认仓库具有 PDG 层，并注明它主要是函数内分析。
11. 只有标准查询无法回答且已读取 `gitnexus://repo/{name}/schema` 时才使用 `cypher`。

将 GitNexus 结果转换为以下证据，不直接转换为业务结论：

| GitNexus 结果 | 可支持的实现证据 |
| --- | --- |
| clusters | 候选功能区域、代码聚合和耦合线索 |
| processes / query | 当前执行流程候选和相关入口 |
| context | 符号职责线索、引用、依赖和参与流程 |
| trace | 两个符号之间可发现的调用路径 |
| impact | 修改符号的潜在影响半径 |
| detect_changes | 当前代码变更影响到的功能和流程 |
| pdg_query | 函数内部控制条件和定义到使用关系 |
| check | 图谱可检查的结构不变量，例如循环依赖 |

## 4. 无 GitNexus 时的回退流程

GitNexus 不可用、目标仓库未索引或索引无法更新时继续分析：

1. 使用文件搜索定位业务术语、入口、状态枚举、接口、事件、作业和数据访问。
2. 从控制器、命令、消费者、定时任务和 CLI 等入口向下追踪调用链。
3. 检查测试、契约、数据库迁移、配置和部署文件，补充代码路径之外的事实。
4. 查找外部调用方、反向依赖、共享数据、批处理、报表、通知和人工修复入口。
5. 记录搜索范围、未覆盖的动态调用、反射、生成代码、运行时配置和外部仓库。

不得因为缺少 GitNexus 而停止概要设计，也不得为了获得图谱而改变生产系统。

## 5. As-Is 基线

至少识别以下内容：

- 当前系统边界、运行单元、部署和外部系统。
- 当前模块或功能区域及实际依赖方向。
- 核心入口、执行流程、状态和数据变化。
- 数据库、共享数据、数据权威方和跨边界写入。
- 对外接口、内部接口、事件、批处理和定时任务。
- 身份、权限、数据范围和信任边界。
- 配置、开关、版本条件和环境差异。
- 日志、监控、告警、审计和人工运维入口。
- 已知缺陷、技术债、临时设计和未解释行为。

为重要行为标记：正式需求、当前实现、实际使用、是否必须兼容、证据和置信度。

## 6. 兼容性维度

| 维度 | 概要设计检查内容 |
| --- | --- |
| 业务行为 | 未明确变更的外部可观察结果是否保持；已知缺陷是否明确处理 |
| 状态兼容 | 存量对象能否进入新流程和状态；终态和非法转换如何处理 |
| 数据兼容 | 历史数据是否可读、迁移、校验、回退、归档和保留 |
| 接口兼容 | 旧调用方、参数、返回、错误语义、版本和弃用窗口 |
| 事件兼容 | 事件语义、顺序、重复、丢失、消费者和版本关系 |
| 权限兼容 | 原有角色、数据范围、服务身份和授权结果是否变化 |
| 配置兼容 | 旧配置、默认值、开关、密钥和环境差异是否仍有效 |
| 部署兼容 | 新旧版本共存、灰度、数据库变更顺序和回滚条件 |
| 运维兼容 | 日志、监控、告警、审计、修复入口和运行手册是否延续 |
| 性能兼容 | 响应、吞吐、批处理、资源消耗和外部调用特征是否变化 |

只检查适用维度，但不得遗漏历史数据、旧调用方、运行中业务和不可逆变更。

## 7. 差异与影响矩阵

为重大变更记录：

| 字段 | 内容 |
| --- | --- |
| 关联需求或决策 | 为什么改变 |
| As-Is | 当前实现和证据 |
| To-Be | 目标行为和架构 |
| Gap | 需要改变和保持的内容 |
| 影响对象 | 模块、数据、接口、事件、作业、配置、部署、运维和调用方 |
| 兼容原则 | 保持、适配、版本化、迁移、双轨、弃用或不兼容 |
| 过渡方案 | 新旧能力如何共存和切换 |
| 回退限制 | 哪些变化可逆，哪些数据或状态不可逆 |
| 验证方式 | 如何证明新行为正确且旧行为未被意外破坏 |
| 证据与置信度 | 文件、符号、流程、运行证据和未知项 |

使用 `impact` 或 `detect_changes` 结果时仍需检查图谱之外的数据库、配置、部署、动态调用、外部仓库和人工流程。

## 8. 过渡、迁移与回退

明确：

- 当前架构、过渡架构和目标架构。
- 新旧能力共存范围、兼容期、流量或调用方切换顺序。
- 历史数据迁移、校验、补录、归档和差异处理原则。
- 接口、事件、配置和数据库版本兼容关系。
- 应用发布、数据变更、后台任务和消费者的执行顺序。
- 临时双写、适配或兼容层的责任和退出条件。
- 监控指标、人工检查和切换停止条件。
- 回滚触发条件、恢复目标和不可逆变更的处置原则。

不要只写“支持回滚”。数据、状态或外部调用已经发生不可逆变化时，说明前向修复、补偿或人工处理方式。

## 9. 验证与输出映射

至少覆盖：

- 未明确变更的行为和旧调用方回归。
- 存量状态、历史数据和边界数据。
- 新旧版本共存、灰度、切换和重复执行。
- 数据迁移数量、关系、状态和业务不变量。
- 权限范围、接口或事件版本和配置默认值。
- 部署顺序、监控、告警、人工入口和回退限制。

## 10. 工具边界

- GitNexus 图谱主要描述仓库内静态结构和可发现流程，不覆盖全部运行时行为。
- 动态调用、反射、生成代码、运行时配置、数据库过程、外部仓库、手工操作和线下流程可能缺失。
- `trace` 未发现路径不证明不存在路径；搜索可能受深度、歧义或索引范围限制。
- `impact` 表示潜在影响，不表示每个结果都一定发生业务变化。
- `pdg_query` 的控制和数据依赖主要是函数内范围，不证明跨函数完整数据流。
- 索引陈旧时降低置信度，不得把旧图谱当作当前实现。
- 代码存在某个判断只证明实现线索，不证明业务正确性、使用频率或未来保留义务。
