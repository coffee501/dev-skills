# 兼容性分析与基线检查

在已有功能变更、业务规则调整、系统集成、数据迁移、功能下线或架构迁移时读取本文件。`brownfield.md` 负责建立存量实现证据和 As-Is 基线；本文件负责判断哪些行为必须保持、如何兼容、能否迁移和回退，以及是否满足概要设计基线。

## 1. 变更类型路由

识别主类型和次类型：

| 类型 | 必查内容 |
| --- | --- |
| 已有功能变更 | 外部行为、状态、调用方、数据和回归范围 |
| 业务规则调整 | 新旧规则适用范围、历史数据、在途业务和报表统计 |
| 系统集成 | 契约、数据权威、失败语义、重复处理、版本和消费者 |
| 数据迁移 | 数据范围、映射、校验、共存、切换、回退和保留 |
| 功能下线 | 调用方、消费者、替代能力、存量数据、审计和退出条件 |
| 架构迁移 | 新旧模块、流量、数据、部署、运维和临时设计退出 |

纯新建系统不读取本文件，除非它需要兼容已有调用方、共享数据、接口、事件、部署环境或运行流程。

## 2. 兼容分析主线

按以下顺序完成分析：

> As-Is → To-Be → Gap → 必须保持不变的行为 → 受影响对象 → 兼容策略 → 迁移与共存 → 回滚 → 验证

对每个重大变化明确：

- 为什么改变，关联哪个 `REQ-CHG` 或 `DEC`。
- 当前行为或契约有哪些直接证据。
- 目标变化是什么，哪些内容明确不变。
- 受影响的角色、流程、状态、数据、接口、事件、调用方和运行单元。
- 兼容是永久约束、过渡措施还是明确的不兼容变更。
- 迁移、共存、退出、回滚和验证如何形成闭环。

## 3. 业务兼容与技术兼容

### 业务兼容

覆盖角色和权限、业务资格、规则、状态、结果、历史数据、在途流程、报表统计和人工处置。业务语义没有确认时：

- 列出当前行为、候选变化及各自影响。
- 将问题返回 `dev-req`。
- 不用技术方案替代业务决策。

### 技术兼容

覆盖接口、事件、数据格式、版本、配置、部署、运行环境和运维入口。`dev-hld` 负责确定总体兼容、版本化、迁移、共存和回退原则；字段映射、适配代码、转换脚本和版本判断交给 `dev-lld`。

业务兼容和技术兼容同时存在时，先确认业务结果，再设计技术手段。

## 5. 重点检查

### 历史数据

- 新规则是否追溯适用，生效时间和边界是否明确。
- 旧数据能否被新版本读取、展示、统计、修改和归档。
- 数据迁移失败、部分迁移和重复执行会产生什么业务结果。
- 回滚后旧版本是否仍能理解已经产生的新数据和新状态。

### 在途业务

- 发布时处于处理中、等待中、重试中或人工介入中的对象有哪些。
- 在途对象继续旧流程、切换新流程还是按状态分流。
- 新旧版本同时处理同一对象时如何避免重复和冲突。
- 临时兼容逻辑何时退出，由谁确认退出。

### 调用方和消费者

- 已识别直接、间接、批量、报表和人工调用方。
- 未掌握源码的调用方仍按外部契约和运行证据纳入影响范围。
- 新增必填字段、返回语义、错误、事件或顺序变化是否破坏旧消费者。
- 版本化、默认行为、弃用窗口和通知责任是否明确。

### 报表、批处理和定时任务

- 新旧状态和数据含义是否影响统计口径。
- 批处理选取条件、重复处理、补数和时间窗口是否变化。
- 下线功能是否仍被报表、导出、通知、对账或修复任务引用。

### 发布和回滚

- 应用、数据库、配置、事件生产方和消费者的发布顺序明确。
- 新旧版本共存时双方都能处理共享数据和契约。
- 回滚不仅恢复代码，还能处理新版本已产生的数据、状态和外部结果。
- 不可逆变化具有前向修复、补偿或人工处理原则。

## 6. 影响分析链

对每个变更需求维护：

> `REQ-CHG → 受影响 DEC → 受影响 MOD → 受影响 FLOW → 数据与接口影响 → 兼容策略 → VAL 回归验证`

检查每个节点：

- 原 `DEC` 是否仍有效，需要修改、废止或替代。
- 模块职责、依赖和数据权威是否变化。
- 正常、异常、在途和恢复流程是否变化。
- 历史数据、接口、事件、报表、批处理、权限和部署是否受影响。
- 兼容策略是否覆盖所有受影响对象。
- `VAL` 是否能证明目标变化生效且未明确改变的行为仍然成立。

## 7. 兼容策略

根据证据选择并说明退出条件：

- **保持兼容**：目标版本继续支持旧行为或契约。
- **默认兼容**：新增能力使用默认值或可选字段，旧调用方无需变化。
- **版本化**：新旧接口、事件或数据格式并存，具有弃用窗口。
- **适配**：在边界转换新旧语义，明确责任方和期限。
- **迁移**：一次或分批转换历史数据、配置或调用方。
- **双轨共存**：新旧流程或系统并行，明确路由、数据权威和退出标准。
- **明确不兼容**：具有业务批准、迁移方案、通知、切换和回退原则。
- **下线**：确认零调用、替代能力、数据处置、审计和清理顺序。

不要默认使用双写、双读、消息队列或兼容层；这些只是可能的详细机制，必须有设计依据。

## 8. 基线阻塞条件

存在以下任一情况时，不得标记为“概要设计基线”：

- 未识别受影响调用方或消费者。
- 历史数据适用规则不明确。
- 在途业务处理方式不明确。
- 新旧版本共存规则不明确。
- 不兼容变更没有迁移方案。
- 回滚后数据或状态无法继续使用，且没有前向修复或补偿原则。
- 兼容风险没有对应 `VAL` 验证项。
- 关键兼容决策仍是 `Proposed`。
- 决定可行性的关键决策缺少验证，或错误标记为 `Validated`。

阻塞时保持“概要设计草案”，列出问题归属、影响范围和解除条件。

## 9. 评审输出

兼容性评审至少输出：

1. 需求类型和兼容检查范围。
2. As-Is、To-Be、Gap 和必须保持内容。
3. 兼容性矩阵。
4. 影响分析链。
5. 兼容、迁移、共存、回滚和退出策略。
6. P0、P1、P2 风险和待确认事项。
7. `DEC` 状态和 `VAL` 覆盖。
8. 是否满足概要设计基线条件。
