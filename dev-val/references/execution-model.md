## 执行原则

使用目标仓库已有的测试框架、命令、CI配置、测试选择器和报告格式。不要为了统一入口而新增测试框架、包装层或依赖。先证明目标所需的最小范围，再按风险扩展；不要机械运行全部测试。

执行前固定被测代码、生成物、契约、配置、依赖锁、数据条件和环境。工作区存在未提交修改时记录其状态和是否属于被测版本，不将未知工作区当作可复现版本。

## RUN批次

一个 `RUN` 表示同一被测版本、环境、授权范围和主要验证目标下的一组执行。任一条件发生实质变化时创建新批次，不静默覆盖旧批次。

至少记录：

| 字段 | 要求 |
| --- | --- |
| `id/change/version/status` | 遵循共享产物信封；无正式CHG时使用临时编号 |
| `objective` | 本批次要证明的行为、风险或门禁目标 |
| `test_refs` | `TC/AUT`或本地`TEST-*`及版本 |
| `target` | 代码、构建、镜像、契约和配置版本 |
| `environment` | 环境身份、拓扑版本、所有者和隔离级别 |
| `data_conditions` | 数据集、敏感级别、生成与清理方式 |
| `commands` | 入口、参数、工作目录、超时和执行顺序 |
| `limits` | 并发、速率、数据量、时长、资源和费用上限 |
| `authorization` | 执行范围及高风险操作依据 |
| `stop_conditions` | 错误率、资源、外部影响和人工停止条件 |
| `attempts` | 每次尝试、原因、开始结束时间和结果 |
| `cleanup` | 计划、结果、残留和恢复责任 |

状态使用 `Planned → Ready → Running → Passed / Failed / Blocked / Aborted`。只有进入条件满足后才能从 `Planned` 进入 `Ready`；命令未运行时不得使用 `Passed/Failed`。

## 测试选择

选择顺序：

1. 用户明确指定且输入可靠的测试。
2. `VAL/DVAL`要求的必选 `TC/AUT`。
3. 变更影响链中的关键和高风险回归。
4. 为解释失败所需的最小诊断测试。
5. 风险或门禁要求的扩展套件。

记录包含项、排除项、条件项和依据。跳过、未运行和隔离不是通过；它们对门禁的影响由聚合规则决定。

## 命令发现与执行

依次检查仓库规则、包管理器脚本、构建配置、CI工作流、已有测试文档和测试代码。优先使用非交互、可设置超时、可选择范围并能生成机器报告的入口。

执行每个命令时记录工作目录、完整参数的安全摘要、开始结束时间、退出码、超时、信号或中断、报告位置及环境差异。不要输出凭据；包含秘密的参数只记录已脱敏形式。

先运行快速就绪检查或单个代表性测试，再运行目标集合。失败后先读取实际输出并分类，不立即重跑、换参数或修改环境。

## 结果模型

每个用例或可识别检查使用 `NotRun/Passed/Failed/Blocked/Skipped`：

- `Passed`：执行完成且可观察结果满足可靠预期。
- `Failed`：执行完成且结果违反预期，或者运行器报告真实失败。
- `Blocked`：环境、权限、数据、依赖或安全条件阻止执行或判断。
- `Skipped`：根据明确规则未执行，必须记录原因。
- `NotRun`：计划内但尚未执行。

运行器进程退出成功不自动表示所有目标通过；退出失败也可能来自测试、环境或基础设施问题。必须结合用例结果、报告完整性和原始输出判断。

## 外部证据导入

导入CI、供应方或人工报告时记录来源系统、执行标识、触发者、时间、被测版本、环境、选择规则、报告完整性、签名或哈希、保留位置和缺失上下文。无法证明版本或环境时保留为弱证据，不用于关键门禁通过。

规范化报告不得丢弃首次失败、跳过、错误、重试和原始定位器。规范化结果是派生证据，不替代原始报告。

## 清理与终止

执行期间持续观察停止条件。达到安全阈值、范围外副作用、资源异常、环境漂移或用户停止要求时终止后续步骤并将 `RUN` 标记为 `Aborted` 或 `Blocked`。

完成后检查测试数据、消息、队列、缓存、临时文件、配置、进程、容器和外部资源。只清理由本批次创建且已确认可删除的对象；保留无法清理的精确记录。
