## 处理原则

保留首次失败、全部尝试和环境变化。先分类，再决定是否重试、隔离或交接；不得通过修改预期、测试、数据或产品实现来消除失败。证据不足时保持 `Unknown`。

## 失败分类

| 类别 | 判定边界 |
| --- | --- |
| `ProductFailure` | 可靠测试在有效环境中违反已确认预期 |
| `TestDefect` | 测试步骤、断言、夹具、替身或自动化实现错误 |
| `EnvironmentFailure` | 环境不可用、配置漂移、资源或基础设施异常 |
| `DataSetupFailure` | 测试数据无法准备、污染、状态或清理不符合条件 |
| `DependencyFailure` | 外部或内部依赖不可用、限流、契约不匹配或权限失败 |
| `FlakySuspected` | 相同输入和条件下结果不稳定且原因未确认 |
| `PolicyBlocked` | 安全、授权、合规、费用或爆炸半径阻止执行 |
| `Unknown` | 当前证据不足以可靠分类 |

运行器退出码只是一项证据，不直接决定类别。多个原因并存时记录主要类别和促成因素。

## DEFECT记录

`DEFECT` 至少包含来源 `RUN/EVD`、失败测试、首次失败、复现步骤、预期来源、实际结果、分类及依据、影响范围、环境和版本、复现性、已尝试诊断、责任流程、剩余未知和重新验证条件。

不要自行分配业务严重度、修复优先级或负责人；缺少授权时只记录观察到的影响和建议责任角色。

## 重试规则

只有以下情况可以重试：

- 已定义的测试或平台重试策略适用。
- 有证据表明短暂环境或依赖问题可能恢复。
- 需要判断失败是否可重复，且重复次数和条件已事先限定。
- 修复、环境恢复或数据重置后执行正式复测。

每次重试记录原因、与首次尝试的条件差异和结果。不得无限重试、选择性展示通过尝试或将最终偶尔通过解释为稳定通过。

## Flaky判定

一次失败后通过只能标记 `FlakySuspected`。确认Flaky需要在可比较条件下存在相互矛盾结果，并排除明确产品、测试、数据或环境原因。记录发生率只用于描述，不用无依据阈值自动确认。

Flaky不等于低风险。关键路径、权限、资金、状态或数据一致性测试的不稳定本身可能阻止门禁通过。

## Quarantine治理

Quarantine是有期限的隔离措施，不是删除或跳过失败。至少记录：测试编号、原因、开始时间、责任方、影响的 `VAL/DVAL`、替代证据、恢复条件、目标期限和过期处理。

关键必选测试被隔离时默认使相关门禁 `Blocked`。只有聚合规则允许、存在充分替代证据且风险由有权限责任方接受时，才可以形成带例外的其他结论。

## 责任路由

- 产品或自动化代码失败：`dev-impl`。
- 用例、预期、数据分区或自动化规格问题：`dev-test`。
- 业务、架构或详细设计语义问题：对应 `dev-req/dev-hld/dev-lld`。
- 环境、凭据、共享服务或平台问题：环境所有者或正式平台流程。
- 生产或发布相关问题：`dev-rel/dev-ops`。

交接时保留可继续执行的测试和未受影响门禁分支。
