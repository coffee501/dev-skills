# 输出与质量契约

在生成完整需求、执行需求评审、判断需求基线或需要固定输出结构时，读取本文件。局部问题只执行与当前范围相关的检查。

## 导航

- 工作模式与输出
- 实现反向需求发现
- 完整需求文档结构
- 需求基线条件
- 最终质量检查

## 工作模式与输出

### 需求诊断

适用于首次收到粗略需求，或用户希望逐步完善需求。输出：

1. 需求理解。
2. 已确认内容。
3. 缺失、歧义与冲突。
4. 主要风险。
5. 需求完整度。
6. 三至五个优先确认问题。

不要直接生成包含大量假设的完整文档。

只有已确认内容可以写为正式需求、规则或验收标准。合理推断应放入单独的“候选项”或“待确认”区域，不分配 `REQ/RULE/AC` 正式编号。完整度按分析维度说明完整、部分明确、缺失、冲突或不适用，不输出无依据的百分比或综合评分。

### 增量完善

适用于用户回答上一轮问题。输出：

1. 本轮确认结论。
2. 新增、修改和废止说明。
3. 更新后的相关需求内容。
4. 新发现的冲突和影响。
5. 未解决问题与完整度变化。
6. 下一批三至五个关键问题。

不要重复询问已经解决的问题，也不要重复输出未受影响章节。

如果本轮回答针对实现反向需求发现产生的 `CAND-*`，继续读取 [实现反向需求流程](implementation-to-requirements.md)，保留候选项与证据，只提升用户或权威资料明确确认的部分；已否决、待确认和已废止候选不得获得正式 `REQ/RULE/AC`。

### 完整输出

适用于用户明确要求完整文档，或信息已经基本充分。输出当前可确定的完整需求，将不能确定的内容标记为待确认，并汇总风险、冲突和未决问题。不要因局部信息不足拒绝输出；存在未解决的 P0 问题时标记为“需求草案”。

根据复杂度裁剪：

- **简单需求**：目标、范围、流程、规则、验收和待确认问题。
- **一般需求**：使用十五点框架中的全部适用章节。
- **复杂需求**：增加对象关系、状态转换、追踪关系和影响分析。

### 需求评审

适用于用户要求检查已有文档。优先输出问题和影响，不重复原文，也不主动重写完整文档：

1. 总体结论。
2. 完整度检查。
3. 需求质量问题。
4. 规则、状态和数据问题。
5. 流程、异常和权限问题。
6. 影响、兼容和回归风险。
7. 验收性问题。
8. 修改建议。
9. 待确认问题。

### 实现反向需求发现

适用于从已有项目、遗留系统、代码或运行行为整理需求。读取 [实现反向需求流程](implementation-to-requirements.md)，输出：

1. 分析目标、仓库版本、环境和证据覆盖范围。
2. 当前能力与用户可见入口清单。
3. As-Is 行为目录及文件、符号、契约、测试、配置或运行证据。
4. 使用 `CAND-*` 标识的候选需求、候选规则和候选验收条件。
5. 证据冲突、版本差异、实现推断和未覆盖范围。
6. 可能需要兼容的行为及依据；没有依据时不得声明必须保持。
7. P0/P1/P2 待确认问题。
8. 已确认并可提升为正式需求的内容，以及仍停留在候选状态的内容。

未经确认不得分配正式 `REQ/RULE/AC`，不得把类、函数、表、字段、框架或技术机制机械改写成需求，也不得把“未发现实现”解释成“系统不存在该行为”。

## 完整需求文档结构

从以下章节选择适用项，不为空模板补内容：

1. 需求背景与概述。
2. 功能目标、非目标与优先级。
3. 适用范围、约束与依赖。
4. 名词、业务对象与数据口径。
5. 用户角色与使用场景。
6. 业务流程与状态流转。
7. 功能需求。
8. 业务规则。
9. 权限与安全要求。
10. 数据要求与一致性。
11. 数据展示与交互要求。
12. 异常、补偿与通知。
13. 操作日志、审计与监控。
14. 非功能、集成与发布要求。
15. 验收标准与需求追踪。

将变更、决策、风险、冲突和待确认问题放在相关章节；只有集中管理更清晰时才使用附录。

## 需求基线条件

仅当以下条件全部满足时，标记为“需求基线”；否则标记为“需求草案”：

- 业务目标、范围和非目标明确。
- 核心对象及边界明确。
- 主流程和关键状态变化明确。
- 核心规则和数据口径明确。
- 主要异常具有预期业务结果。
- 关键需求具有验收标准。
- 影响范围和质量要求已经识别。
- 不存在未解决的规则冲突或 P0 问题。

## 最终质量检查

- 没有虚构业务事实，也没有把推断写成正式规则。
- 正式编号只用于已确认内容；候选项和待确认项没有伪装成正式需求。
- 实现反向需求中的每个 `CAND-*` 都有具体证据、版本、适用范围、置信度和确认状态。
- 没有把当前实现自动写成正确的 To-Be，也没有把技术结构机械翻译成业务需求。
- 代码、测试、契约、配置、文档和运行证据的冲突及未覆盖范围没有被隐藏。
- 没有用技术假设替代业务确认或越界进入详细设计、测试步骤。
- 已区分 As-Is、To-Be 和 Gap，并识别规则冲突。
- 对象、状态和数据语义一致。
- 每个核心操作都有角色、条件、结果和异常业务结果。
- 已识别影响、兼容、回归和质量风险。
- 核心需求、规则和验收标准可追踪。
- 待确认问题按 P0/P1/P2 排序，且没有重复询问。
- 完整度使用维度状态，没有无依据百分比或综合评分。
- 没有重复结论、空章节或无依据清单。

优先使用表格表达对象关系、状态转换、数据变化、角色权限、规则、风险和验收标准，但仅在表格明显提升清晰度时使用。
