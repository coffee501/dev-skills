# 实现反向需求流程

从已有项目、遗留系统、代码、测试、契约、配置、数据结构或运行资料中整理需求时读取本文件。目标是建立可追溯的 As-Is 行为和候选需求，而不是把当前实现自动包装成正确的 To-Be。

## 核心原则

- 从用户可观察行为出发，不从代码目录、类、函数、表或技术组件出发组织需求。
- 区分“实现存在”“测试断言”“契约承诺”“运行发生”和“业务确认”。
- 把已有实现视为 As-Is 证据、兼容线索和问题来源，不自动视为正确需求或未来保留义务。
- 每项重要结论附证据位置、版本、适用范围、置信度和未知项。
- 未确认内容只使用 `CAND-*`，不得进入正式 `REQ/RULE/AC` 或需求基线。
- 冲突证据并列保留，不以代码、测试、文档或运行行为中的任一方静默覆盖其他来源。

## 证据模型

| 证据类别 | 可支持的结论 | 不能单独证明 |
| --- | --- | --- |
| 业务确认 | 目标、业务规则、必须保持的行为 | 未明确的边界和异常 |
| 正式需求或决策 | 历史目标、批准规则和验收语义 | 当前实现仍然符合 |
| 运行证据 | 实际发生的路径、结果、频率和使用强度 | 行为正确或未来必须保留 |
| 对外契约 | 外部可观察输入、输出和兼容承诺 | 内部业务目的和全部隐含规则 |
| 测试证据 | 被断言的行为、边界和回归意图 | 断言代表正确业务规则 |
| 实现证据 | 当前版本存在的路径、判断、状态变化和副作用 | 生产必然执行或业务要求正确 |
| 配置或数据证据 | 条件开关、默认值、约束和数据形态 | 权威业务口径及未来默认值 |
| 推断 | 多项证据支持的候选解释 | 正式需求结论 |

重要证据记录以下字段：

- 仓库、版本或提交、环境和采集时间。
- 文件、符号、契约、配置、数据或运行资源。
- 证据类别、直接结论、适用范围和新鲜度。
- 高、中或低置信度，以及降低置信度的原因。
- 冲突来源、未覆盖路径和需要确认的问题。

## 分析边界

1. 明确目标功能、用户入口、仓库、版本、环境和输出用途。
2. 用户要求分析整个项目时，先建立业务能力和入口清单，再按业务域或用户任务分批深入。
3. 记录未覆盖的动态调用、反射、生成代码、数据库过程、运行时配置、外部仓库、第三方系统和人工流程。
4. 缺少运行环境或日志时，只能形成实现事实和候选行为，不声明生产使用情况。
5. 目标版本不明确时先标记范围问题，不把多个版本的行为合并为单一现状。

## 证据发现

按以下顺序建立证据地图：

1. 定位页面、命令、公开 API、事件、任务或其他用户可见入口。
2. 沿主路径识别参与角色、前置条件、校验、权限和数据范围。
3. 记录业务对象、状态转换、数据变化、计算结果和外部副作用。
4. 检查拒绝、异常、超时、重复、并发、部分成功、取消、撤销和补偿路径。
5. 检查通知、审计、报表、定时任务、外部系统和人工处理入口。
6. 使用测试、契约、配置、迁移、文档和运行资料交叉验证实现线索。
7. 记录搜索范围及未发现证据的区域；“未发现”只表示当前范围未覆盖或未定位。

GitNexus 或其他代码图谱工具可用于定位功能聚类、入口、调用路径和影响半径，但工具结果只能作为实现证据。聚类名称不能直接成为业务模块，调用关系不能直接成为业务职责。工具不可用时使用仓库搜索、入口追踪、测试、配置和契约检查，不阻塞分析。

## As-Is 行为目录

按以下闭环描述当前行为：

> 角色 → 触发条件 → 业务操作 → 状态与数据变化 → 业务结果 → 异常结果 → 外部影响

对每项行为标记：

- **直接事实**：证据直接显示某个实现、契约或运行结果。
- **交叉佐证**：两个或以上独立来源支持相同解释。
- **行为推断**：从实现结构推导的候选解释，仍需确认。
- **未知**：分析范围不足或证据冲突，无法形成结论。

不要把技术日志、内部调用、缓存变化或数据库写入直接写成业务结果；只有用户、上下游或业务数据可观察的结果才进入行为目录正文，技术信息保留在证据栏。

## 实现线索转换

| 实现线索 | 可形成的候选需求语义 | 转换限制 |
| --- | --- | --- |
| 页面、命令或公开入口 | 参与角色、触发场景和业务能力 | 入口存在不证明未来必须保留 |
| 授权判断和数据过滤 | 当前权限条件和数据范围 | 不自动定义目标角色模型 |
| 校验分支和错误结果 | 候选允许、拒绝和异常规则 | 技术异常不能直接成为业务规则 |
| 状态枚举和转换 | 候选生命周期、合法转换和终止状态 | 未发现转换不等于业务禁止 |
| 计算、阈值和默认值 | 候选计算、限制或默认规则 | 常量和配置值必须确认业务依据 |
| 数据约束和关联 | 候选唯一性、不变量和对象关系 | 表结构不等于业务对象边界 |
| 重试、超时和补偿 | 当前失败后的业务结果和最终状态 | 不把队列、锁或重试机制写入需求正文 |
| API、事件和任务 | 集成触发、输入输出和外部影响 | 不复制路径、字段和中间件实现 |
| 测试用例和断言 | 候选验收场景、边界和拒绝结果 | 与实现同源的测试不是独立业务确认 |
| Feature Flag 或环境配置 | 条件适用范围和版本差异 | 不推广为全局规则 |

## 候选需求

使用当前分析范围内的 `CAND-001`、`CAND-002` 等临时标识。每项包含：

| 字段 | 要求 |
| --- | --- |
| 临时标识 | 仅用于本次分析关联，不进入正式追踪链 |
| 候选业务要求 | 使用实现中立、用户可观察的业务语言 |
| As-Is 行为 | 当前版本在已知条件下的表现 |
| 来源证据 | 文件、符号、契约、测试、配置或运行资源 |
| 适用范围 | 版本、环境、租户、角色、对象或数据范围 |
| 置信度 | 高、中、低及理由 |
| 冲突与未知 | 相反证据、缺失路径和未确认语义 |
| 兼容影响 | 依赖方是否可能观察或依赖该行为 |
| 确认状态 | 待确认、已确认、已否决或已废止 |

无法从实现证明的业务目标、必要性、责任角色、未来保留义务、权威数据口径和质量指标必须标为待确认。实现细节无法安全转换成业务结果时，保留为证据，不生成候选需求。

## 候选验收条件

- 只为证据充分、外部可观察的行为形成候选 Given / When / Then。
- 标明 oracle 来源是业务确认、运行、契约、测试、实现还是推断。
- 覆盖适用的正常、拒绝、边界、权限、重复、并发、异常和兼容场景。
- 不使用被分析实现的内部算法或同源查询生成目标预期。
- 不展开完整测试步骤、测试数据或自动化实现。

候选验收条件仍属于 `CAND-*`。未经确认，不分配正式 `AC-*`，也不宣称现有测试已经证明需求正确。

## 确认与正式提升

1. 让用户或权威资料逐项确认候选业务语义、适用范围和是否需要保留。
2. 只提升已确认部分；同一流程中的其他候选项继续保持原状态。
3. 将已确认候选转换为实现中立的需求、规则和验收条件，再分配正式 `REQ/RULE/AC`。
4. 保留 `CAND-*` 与正式编号的来源关系，但不把临时编号冒充正式历史编号。
5. 用户否决候选项时记录否决依据；用户替换现状时建立 As-Is、To-Be 和 Gap。
6. 存在 P0 语义缺口、关键证据冲突或范围未知时，只能形成“需求草案”。

## 输出要求

默认输出：

1. 分析目标、仓库版本、环境、证据范围和未覆盖范围。
2. 当前能力与用户可见入口清单。
3. As-Is 行为目录及证据和置信度。
4. 候选需求、候选规则和候选验收条件。
5. 证据冲突、版本差异和无法确认内容。
6. 可能需要兼容的行为及依据；没有依据时不得声明必须保持。
7. P0/P1/P2 待确认问题。
8. 已确认并可提升的内容，以及仍停留在候选状态的内容。

优先使用以下表格：

| 临时标识 | 候选业务要求 | As-Is 证据 | 置信度 | 冲突/未知 | 兼容影响 | 确认状态 |
| --- | --- | --- | --- | --- | --- | --- |
| `CAND-001` |  |  |  |  |  | 待确认 |

## 停止与交接条件

- 已覆盖目标范围并形成证据化候选需求后停止继续扫描；不要为增加文件数量而扩大分析。
- 需要确认业务目标、规则、状态、数据语义或验收时留在 `dev-req`。
- 需要分析架构边界、模块职责、调用影响、架构迁移、技术迁移方案或技术兼容方案时交给 `dev-hld`；数据迁移的业务范围、新旧口径、历史数据处理规则和验收条件留在 `dev-req`。
- 需要字段、接口、算法或代码级设计时交给 `dev-lld`。
- 需要修改实现时交给 `dev-impl`；反向分析本身不授权修改代码。
