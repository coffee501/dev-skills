# Dev REQ

将粗略、模糊或不完整的业务需求整理成范围明确、规则一致、可追踪和可验收的需求文档，为概要设计和测试设计提供可靠输入。

## 接入 Dev 生命周期

跨阶段变更、增量变更、缺陷、迁移、下线或基线交接应复用已有 `CHG`。没有权威编号时使用临时 `CHG-PENDING-001`，明确其非全局唯一。正式产物记录编号、版本、状态、来源、责任角色和适用范围。

按需读取 Dev 体系协议：

- 需要正式产物信封、编号或追踪链时，读取 [产物协议](../dev-lc/references/artifact-contract.md)。
- 发生责任转移、阶段推进、阻塞返回或失效通知时，读取 [交接协议](../dev-lc/references/handoff-contract.md)。
- 需求语义变化时，读取 [失效传播规则](../dev-lc/references/invalidation-rules.md)，只输出潜在受影响对象，不直接改写下游状态或证据。

如果上述套件协议不可用，继续完成需求分析，但将正式编号、跨阶段状态、交接和失效结论标记为待确认，不虚构协议内容或宣称完成正式交接。

## 保持职责边界

聚焦业务为什么做、需要做什么以及必须保证什么。默认不要输出：

- 系统架构、模块和详细设计。
- 数据库表、字段、索引、接口路径、参数和错误码。
- 类、函数、算法、代码片段和技术实现机制不得进入需求正文。
- 框架、组件、中间件或技术选型。
- 完整测试步骤和测试数据。

可以描述页面或接口的用户可观察业务行为，但不要预设技术实现。实现反向需求发现可以在独立证据栏或证据附录中引用简洁的文件、符号、契约、测试和配置位置，不复制源代码片段，也不把这些证据写进需求正文。技术问题若暴露业务决策缺口，将其转成待确认问题。用户明确扩大任务时，说明职责边界变化后再处理。

## 建立可信输入

读取用户提供的需求、项目资料、已有实现证据及当前对话中已确认的内容，并区分：

存在符合共享资格规则的 `Eligible CTX` 及其引用的 `CTXF/CTXP/CTXG` 时，优先将其作为As-Is实现证据，避免重复扫描；只使用与当前业务
问题相关的裁剪视图。`CTX` 不构成业务确认，`CTXG` 必须保留为待确认或冲突，不能直接转成正式需求。

- **已确认**：可写入正式需求。
- **合理推断**：有上下文支持但尚未确认。
- **待确认**：缺失、冲突、模糊或需要决策。
- **已废止**：已被新决策明确替代。

不得把合理推断写成正式业务规则、正式编号或验收承诺；只能将其标记为候选项并等待确认。按以下顺序判断可信度：

1. 用户当前明确确认的结论。
2. 当前项目正式需求资料。
3. 已确认的历史决策。
4. 现有系统和代码反映的当前行为。
5. 上下文推断和行业惯例。

将现有行为视为 As-Is，不自动视为正确的 To-Be；将行业惯例仅作为发现问题的线索。发现冲突时列出内容、来源和影响，不自行裁决。

区分业务确认、正式需求、运行证据、对外契约、测试证据、实现证据、配置或数据证据以及推断。代码路径只能证明当前版本存在相应实现；测试只能证明某项行为被断言；配置只能证明特定条件下可能生效。它们都不能单独证明业务意图、生产实际使用、未来保留义务或目标质量指标。

## 选择工作模式

根据用户目标选择一种主模式；用户明确指定时以用户要求为准：

- **需求诊断**：首次收到粗略需求或需要逐步澄清。先指出理解、缺口、风险和优先问题，不生成充满假设的完整文档，不为未确认内容分配正式编号。
- **增量完善**：用户补充了答案。只更新受影响内容、冲突、影响、完整度和下一批问题，不重复已解决问题。
- **完整输出**：用户要求完整文档或信息基本充分。输出可确定内容并标记待确认项；存在未解决 P0 时标记为“需求草案”。
- **需求评审**：检查已有需求。优先报告问题、影响和建议；除非用户要求，不重写全文。
- **实现反向需求发现**：用户要求从已有项目、遗留系统、代码或运行行为整理需求。先建立带版本和范围的 As-Is 证据，再形成候选需求、候选规则、候选验收条件和待确认问题；未经确认不得生成正式需求或需求基线。

执行需求评审、实现反向需求发现、需要固定输出结构、生成完整文档或判断基线时，读取 [输出与质量契约](references/output-contracts.md)。

用户对 `CAND-*` 做出确认、否决或补充后，以“增量完善”为主模式，同时继续读取 [实现反向需求流程](references/implementation-to-requirements.md)，保留候选项、证据、确认状态与正式 `REQ/RULE/AC` 的来源关系。

## 识别需求类型

明确主类型，并保留适用的次类型：

- **新增功能**：目标、范围、对象、流程、规则和验收。
- **功能变更**：As-Is、To-Be、Gap 和兼容影响。
- **缺陷修复**：触发条件、实际结果、预期结果和影响范围。
- **规则调整**：新旧规则、生效时间、优先级和历史数据。
- **系统集成**：数据权威、责任边界、失败处理和一致性。
- **数据迁移**：新旧口径、范围、历史数据和验证方式。
- **功能下线**：依赖、存量数据、替代流程和兼容影响。
- **合规要求**：适用范围、安全、隐私、审计和数据保留。

已有功能必须区分 As-Is、To-Be 和 Gap。

## 执行需求分析

按当前问题所需深度执行：

1. 明确目标、范围、非目标和成功指标。
2. 识别参与者、业务对象及关系。
3. 梳理触发条件、流程和状态变化。
4. 明确规则、数据定义和一致性要求。
5. 补充权限、异常、并发和上下游影响。
6. 明确质量属性、约束和发布影响。
7. 将核心需求转成验收标准。
8. 汇总风险、冲突、假设和待确认问题。
9. 判断当前产物是草案还是满足基线条件。

持续检查业务闭环：

> 业务目标 → 参与角色 → 业务对象 → 触发条件 → 业务操作 → 状态与数据变化 → 业务结果 → 异常结果 → 验收方式

创建完整需求、评审完整度，或需要深入检查某一维度时，读取 [十五点需求分析框架](references/requirement-framework.md)。局部问题不必加载或输出完整框架。

## 从已有实现发现候选需求

用户要求将已有实现转成需求时，读取 [实现反向需求流程](references/implementation-to-requirements.md)。从用户可观察入口、公开契约或运行行为开始追踪，检查角色、条件、流程、状态、数据结果、权限、异常和外部影响，不从类、函数、表或技术组件机械生成业务需求。

使用本次分析内的 `CAND-*` 临时标识关联证据和确认状态；它不属于 Dev 正式追踪链。只有用户或权威资料确认后，才将对应内容提升为正式 `REQ/RULE/AC`。代码、测试、文档和运行证据冲突时并列保留来源、版本和影响；“未发现实现”不得解释为“系统不存在该行为”。

需要分析架构、模块职责、调用影响、架构迁移、技术迁移方案或技术兼容方案时交给 `dev-hld`；数据迁移的业务范围、新旧口径、历史数据处理规则和验收条件仍由本 Skill 负责。本 Skill 只将实现证据转换为业务可观察的 As-Is 行为和候选需求语义。

## 管理确认问题

提问前先从现有材料寻找答案。每轮默认只提出三至五个问题，并按影响排序：

- **P0**：影响目标、范围、核心流程、状态、规则或数据口径。
- **P1**：影响权限、异常、并发、依赖、质量属性或验收。
- **P2**：影响体验、审计或后续优化。

一次只确认一个关键决策；优先询问能解除多个阻塞的问题；使用具体场景，必要时提供互斥选项和业务影响。可以推荐但不得代替用户决定。用户要求直接输出时，将问题保留为待确认项，不阻塞其他可靠内容。

## 管理变更与追踪

新信息改变已确认需求时：

1. 判断范围是扩大还是缩小。
2. 识别受影响的对象、流程、状态、规则和验收标准。
3. 说明新增、修改和废止内容。
4. 保留旧结论，用户确认后将其标记为已废止。
5. 更新相关需求和追踪关系。

用户只要求文字优化时，不改变业务含义。

需求逐渐成熟且相关内容已确认后，为核心内容分配稳定标识：`REQ-001`、`RULE-001`、`AC-001`。建立“信息来源 → 需求 → 业务规则 → 验收标准 → 影响对象或流程”的追踪关系；每条核心规则至少关联一条验收标准，每条验收标准可追溯到需求或规则。简单需求不强制编号。

## 保证需求可验收

检查每条正式需求的单一性、必要性、明确性、一致性、完整性、可验证性、可追踪性和实现中立性；将可行性约束交给后续设计评估。完整度按维度标记为完整、部分明确、缺失、冲突或不适用，不使用无依据的百分比或综合评分。

核心需求优先使用 Given / When / Then：

- **Given**：角色、前置状态、权限和业务条件。
- **When**：业务操作。
- **Then**：状态、数据、结果和关联影响。

验收应覆盖正常、拒绝、边界、权限、重复和并发、异常补偿、数据一致性、兼容与回归，但只定义验收条件，不替代 `dev-test` 生成完整测试用例。

## 形成下游输入

- 向 `dev-hld` 提供需求基线、业务对象和边界、核心流程和状态、规则与数据约束、权限、异常、质量要求、影响、风险和未决问题。
- 向 `dev-test` 提供需求与规则标识、验收标准、状态转换、数据边界、权限矩阵、异常和兼容场景。

存在未解决 P0 时，明确其影响，不使用设计假设掩盖需求缺口，也不得宣称需求已形成基线。
