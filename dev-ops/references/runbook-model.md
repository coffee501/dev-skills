# Runbook 模型

## 适用原则

Runbook把已知操作转化为可核对、可停止、可恢复的步骤。它不是知识随笔、命令仓库或授权凭证，也不能替代操作者对当前上下文的确认。

## 最小结构

| 部分 | 必须说明 |
| --- | --- |
| 身份 | ID、名称、版本、状态、所有者、更新与复审时间 |
| 目标 | 要解决的症状或运行任务，以及明确非目标 |
| 触发 | 告警、观察、业务条件和进入阈值 |
| 范围 | 环境、服务、租户、区域、版本、数据和不适用条件 |
| 前置 | 当前状态、依赖、窗口、权限、备份、监控和沟通准备 |
| 目标解析 | 如何得到精确资源，如何核对账号/环境，禁止的通配方式 |
| 步骤 | 动作、参数、预期结果、最大影响面和每步后置检查 |
| 停止 | 何时不继续、何时回退、何时升级 |
| 恢复 | 撤销临时动作、恢复流量/配置/数据和失败时策略 |
| 验证 | 业务、技术、数据、依赖与观察窗口 |
| 证据 | 审计、日志、输出、快照和时间线位置 |
| 升级 | 责任角色、供应方、沟通受众和响应时间 |
| 生命周期 | 演练、适用版本、依赖变化、复审周期和退出条件 |

## 步骤写法

每一步使用“检查 → 动作 → 预期观察 → 停止/下一步”结构。命令使用项目已有工具和显式参数，不嵌入真实密钥，不使用未解析占位符。高风险动作单独成步，不能与查询或验证串成一个不可中止的批处理。

示例中的标识只能是安全占位符；执行前必须解析成精确目标并再次核对。Runbook应描述意图和核验点，不为了看似完整而复制大量易过期命令输出。

## 评审与演练

进入 `Ready` 前至少验证：

- 触发和不适用条件可判断。
- 最小权限和实际工具入口可用。
- 目标解析不会默认落到错误生产环境。
- 每个有副作用步骤都有停止与恢复路径。
- 验证信号能够覆盖业务影响而非仅进程状态。
- 演练、历史执行或等价证据支持步骤可行。
- 责任、升级和复审日期明确。

无法在生产等价环境演练时，记录未验证部分、替代证据和额外操作安全门。

## 失效与复审

以下变化使相关Runbook进入 `NeedsReview`：拓扑或版本变化；平台、命令或权限变化；依赖或供应方变化；SLO、告警或业务规则变化；事故暴露步骤错误；恢复、备份或数据结构变化；实际执行偏离手册。

Runbook过期不表示知识无价值，但不得在未经复核时作为L3/L4执行依据。被新手册替代时进入 `Superseded` 并保留引用；能力退出时进入 `Deprecated`。

## 执行后反馈

记录每步是否按手册执行、偏差原因、耗时、失败点、额外人工判断、验证结果和建议更新。不要在事故时间线中静默改写Runbook；先记录偏差，事后创建新版本并复审。
