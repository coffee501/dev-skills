# RCA 与 CAPA

## 原则

复盘用于学习和修复系统控制，不用于追责叙事。事故恢复后再系统分析，但关键证据应在响应期间保全。保持事实、假设、因果结论和改进建议分离。

## RCA 最小内容

1. 事故与影响摘要：范围、持续时间、用户/业务/数据影响和恢复结果。
2. 证据质量：来源、覆盖、时钟、盲区、冲突和限制。
3. 事实时间线：关键变化、检测、决定、行动、恢复和沟通。
4. 触发事件：使系统进入失败路径的变化或条件。
5. 直接机制：具体组件、状态、数据或契约如何产生影响。
6. 促成条件：容量、隔离、默认值、人工界面、依赖、流程等为何允许影响扩大。
7. 控制失效：预防、检测、止损、恢复或验证控制为何未生效。
8. 检测与响应缺口：发现时延、误报/漏报、Runbook、权限、工具、沟通和决策问题。
9. 已排除路径与未解决问题：说明证据和认知边界。
10. CAPA与验证：每项措施对应因果或控制缺口。

## 因果要求

“人为失误”“配置错误”“网络抖动”“依赖故障”通常只是近因或标签。继续追问：系统为何允许该动作、为何影响未被隔离、为何检测/回退未及时发生、为何当前控制不能防止复发。

五问、故障树或因果图可作为辅助，但不强制固定模板，也不能代替证据。每条因果边说明支持证据、反证和置信度。无法确认时保留假设，不强行选择单一根因。

## RCA 状态

- `Draft`：结构和范围已建立。
- `Investigating`：证据、假设和排除路径仍在形成。
- `Reviewed`：相关技术、业务、数据和运行责任方已评审。
- `Accepted`：有权限责任方确认结论可作为改进依据。
- `Superseded`：新证据或新版本替代旧结论。

Skill可建议 `Reviewed/Accepted`，不能代替项目责任方接受结论。

## CAPA 设计

每项措施必须包含：纠正/预防类型、对应RCA或缺口、明确目标、责任角色、期限、目标模块、实施状态、验证方法、成功条件、证据、残余风险和失效条件。

优先选择可验证的系统性控制，例如：限制危险状态、减少错误默认值、缩小爆炸半径、增加不变量校验、改善诊断信号、自动化安全恢复、覆盖具体回归。避免仅写培训、提醒、加强关注或“优化”。

## 路由与验证

| 措施类型 | 主要路由 | 典型验证 |
| --- | --- | --- |
| 业务规则/SLO | `dev-req` | AC和业务指标 |
| 架构隔离/容灾 | `dev-hld` | 设计验证、故障演练 |
| 事务/契约/恢复机制 | `dev-lld` | DVAL、兼容与异常路径 |
| 代码/配置/工具 | `dev-impl` | BUILD、评审和目标测试 |
| 场景/回归缺口 | `dev-test` | 新用例与自动化规格 |
| 证据/门禁 | `dev-val` | RUN/EVD/GATE |
| 紧急或常规修复发布 | `dev-rel` | REL/DEP/MIGRUN/OBS |
| Runbook/告警/值守 | `dev-ops` | 演练、检测和操作验证 |

## CAPA 状态与关闭

- `Proposed`：措施和验证目标已描述。
- `Approved`：责任、范围、期限和资源已确认。
- `InProgress`：目标模块正在实施。
- `Verified`：预定义验证成功，证据有效。
- `Closed`：责任方确认完成、残余风险和后续监控。
- `Cancelled/Superseded`：记录理由、替代项和风险处置。

实现完成不等于验证通过，验证通过也不自动等于关闭。逾期、范围变化、上游失效或验证失败时重新打开或建立替代措施，不能静默关闭。

## 质量检查

拒绝以下浅层结论：无证据的单一根因；把责任人当根因；CAPA与因果链无对应；所有措施都只增加监控；没有所有者/期限；没有可失败的验证条件；事故复发但旧RCA/CAPA未重新评估。
