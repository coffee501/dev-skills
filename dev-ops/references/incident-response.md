# 事故响应

## 响应目标

优先保护人员、数据、安全和业务连续性，在不扩大未知影响的前提下尽快止损并恢复。快速不等于跳过目标解析、授权、证据和停止条件。

## 事故入口

来自告警、用户反馈、客服、业务指标、审计、安全信号、供应方或发布观察。记录来源、首次发现时间、事件时间、当前时间、时区和可信度。重复告警可以归并，但原始定位器必须保留。

## 分诊

先回答：

- 谁受影响，影响什么业务结果，开始于何时，是否仍在扩大？
- 哪些环境、租户、区域、版本、数据和依赖受影响或尚未确认？
- 是否涉及安全、隐私、合规、资金、不可逆数据或人身风险？
- 最近有哪些发布、配置、流量、依赖、证书、容量或数据变化？
- 当前最重要的未知项是什么，什么证据能最快区分假设？

事故等级采用项目现有政策。没有政策或授权时，只陈述影响事实、时间敏感性和建议升级对象，不自行定级。

## 指挥循环

1. 建立单一 `INC` 和当前状态摘要。
2. 指定或识别指挥、操作、调查、沟通和记录责任。
3. 冻结事实、假设、决定、行动和未知项的区分。
4. 选择最小可逆止损动作，检查授权和停止条件。
5. 执行动作并保存前后证据。
6. 评估影响、假设和下一步；证据不支持时及时撤销假设。
7. 按项目节奏更新沟通，直到恢复与交接完成。

每轮只扩大经过验证的动作范围。未知异常、权限变化、数据不变量破坏或安全信号出现时立即升级。

## 止损与缓解

优先次序取决于影响，但通常先选择：阻止继续损坏；隔离故障单元；降低流量或关闭已有功能开关；切换到已批准的降级路径；恢复容量或依赖；执行已批准回滚/恢复。

止损可能降低功能、吞吐或新鲜度，必须记录受影响用户、业务代价、允许时长和退出条件。临时缓解不能自动成为永久设计。

## 沟通

每次更新包括：已确认影响、当前状态、已采取动作、结果、仍在调查内容、下一次更新时间和责任入口。对外沟通遵守项目权限、法律和合规流程；不得推测根因、透露敏感细节或给出未经授权的承诺。

保持技术行动与沟通记录一致。时间线修正应新增更正条目，不能覆盖原始发布内容。

## 状态推进

- `Detected`：事件已发现，影响尚未完整分诊。
- `Triaged`：范围、影响、责任和首要路径足够明确。
- `Mitigating`：正在执行受控止损或恢复动作。
- `Recovered`：声明影响经过业务与技术信号验证，进入稳定观察。
- `RCA`：恢复后进入正式分析和改进跟踪。
- `Closed`：项目责任方确认复盘、交接和必要CAPA治理满足关闭政策。

状态可因反证回退。例如观察窗口内影响复发时，`Recovered` 应回到 `Mitigating` 或重新分诊，而不是保持表面恢复。

## 交接班与外部依赖

交接必须给出当前事实、影响、假设及置信度、已做动作、禁止重复动作、下一步、关键联系人、凭据/平台入口、观察阈值和下一更新时间。供应方事故需保存供应方事件号、状态、承诺、限制和内部影响，不把供应方声明直接当作本系统恢复证据。
