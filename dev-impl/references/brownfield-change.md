# 存量实现与变更分析

## 建立 As-Is

记录入口、核心符号、调用链、数据访问、接口与事件、任务、配置、依赖、部署单元、现有测试和已知运行行为。区分代码事实、运行证据、设计推断和业务待确认。

GitNexus可用于发现功能聚类、调用路径和影响半径；使用前检查仓库与索引新鲜度。工具不可用时使用 `rg`、测试、契约、配置和部署资料。不得把未发现路径解释为不存在行为。

## 变更主线

> `As-Is → To-Be → Gap → Impact → Preserved Behavior → Minimal Change → Regression → Recovery`

检查直接调用方、间接调用方、消费者、共享数据、配置开关、任务、报表、脚本、部署和运维入口。动态配置、反射、插件、消息和数据库耦合不能仅靠静态调用图排除。

## 行为保持

重构和缺陷修复前建立能证明保持项的最低层可靠验证。已有测试只证明当前被检查的行为；若断言不足、过时或固化错误行为，先修正测试规格或交接预期问题。

缺陷修复至少覆盖原始触发、根因条件、邻近边界、重复或并发变体以及不应改变的行为。条件允许时保留修复前失败和修复后通过证据，但正式 `EVD`仍由 `dev-val`产生。

## 影响分类

- **Confirmed**：代码、契约、数据或运行证据证明受影响。
- **PotentiallyAffected**：存在合理路径但缺少决定性证据。
- **NotAffected**：具有可审计边界和排除依据。
- **Unknown**：缺少信息，形成交接或验证要求。

不要用“文件未修改”作为唯一的不受影响依据。
